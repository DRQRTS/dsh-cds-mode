# 审计与留痕（全程可追溯）

> **护栏 6：所有工具调用、决策、权限、Agent 间消息全程留痕。**
> 审计不是"事后补文档"，是**动作的一部分** —— 没留痕的动作等于没发生（且违规）。

---

## 一、留痕的三个层次

| 层 | 内容 | 落盘位置 |
|---|---|---|
| **动作层** | 工具调用、参数、返回码、生效范围 | `.cds/audit.md` |
| **决策层** | 谁在什么时候做了什么判定、依据什么 | `.cds/decisions.md` |
| **通信层** | Agent 间消息（含动作意图） | `.cds/channel/log.md` |

三层**缺一层都算留痕不全**。常见缺陷是只记动作不记决策 —— 结果事后没人知道"当时为什么这么判"。

---

## 二、`.cds/audit.md` 字段规范

追加式。**任何人不得修改他人条目**（发现自己写错 → 追加一条更正，不删原条目）。

```yaml
- audit_id: AUD-2026-0417-01
  time: 2026-10-01T03:41:22+08:00        # 必须含时区
  actor: I-web1                           # 谁做的
  layer: action                           # action | decision | message
  action: "切断 3 台主机出站（白名单化）"
  target: ["10.0.20.14", "10.0.20.31", "10.0.20.44"]
  params: { mode: "egress-whitelist", duration: "4h" }
  gate: { req_id: REQ-041-a, decision: allow, audit_ref: AUD-2026-0417-01 }
  user_credential: null                   # 低风险无需凭据
  basis: ".cds/authorization.md §2 资产清单第 3–5 项"
  result: { status: ok, return_code: 0, effective: "3 台出站连接数 47→3" }
  rollback: { method: "恢复默认放行策略", eta: "5m", executed: false }
```

**关键字段的填写要求**：

| 字段 | 要求 |
|---|---|
| `time` | **必须含时区**。少一个时区标注，B-web2 会在取证时打回 |
| `action` | 具体到参数，不写"加强防护" |
| `target` | 逐个列出，不写"相关主机" |
| `basis` | 具体到授权条款，不写"根据授权" |
| `result.effective` | **可观察证据**，不写"已下发" |
| `rollback` | 含方式与预计耗时；已回滚要标 `executed: true` |
| `gate` | 走策略门的动作必须填；免审批的填 `null` |

## 三、Agent 间消息的留痕（通信层）

护栏 6 明确要求 **Agent 间消息**也留痕。这是"不经晨传话"的必要配套 ——
**没有留痕的直连协同是不可审计的协同，等于把晨的知情权也一起绕过了。**

每条消息落 `.cds/channel/log.md`：

```yaml
- msg_id: MSG-2026-0417-088
  time: 2026-10-01T03:44:10+08:00
  from: A-web2
  to: B-web5
  kind: handoff                  # handoff | action_request | result | reject | alert
  summary: "IOC 清单 11 条，请对照流量找 C2"
  artifact: "security/A-web2-threat-intel.md"
  triggers_gate: false           # 是否含改变系统状态的动作意图
  gate_ref: null
```

**`kind: action_request` 且 `triggers_gate: true` 的消息** —— 即"要改变系统状态"的请求 ——
**必须同时出现在 `.cds/audit.md`**（有策略门判定记录）。只在 channel 里说一声就动手，是违规。

## 四、防篡改

| 措施 | 说明 |
|---|---|
| **追加式写入** | 只追加，不修改既有条目 |
| **更正走追加** | 写错了追加更正条目，引用原 `audit_id` |
| **哈希链（可选，高保障场景）** | 每条含前一条的哈希，形成链式防篡改 |
| **时间戳来源** | 统一取同一时源；跨机时注意时钟漂移 |

**为什么要追加式**：审计的价值在于**能证明"当时真的是这样"**。可随意修改的审计记录，在事后追责或法律场景里没有证明力。

---

## 五、保留期与归档

| 类型 | 建议保留期 | 依据 |
|---|---|---|
| 动作审计 | **≥6 个月**（合规常见要求） | 等保要求网络日志≥6个月 |
| 事件报告 | ≥3 年 | 事件复盘与法律举证 |
| Agent 间消息 | ≥6 个月 | 与动作审计同期 |
| 取证材料 | **按法律要求，通常≥案件时效** | 可能作为证据 |
| 个人数据相关 | 按最小化原则，**到期删除** | D-web4 决定 |

**涉及个人数据的审计记录要过 D-web4**：审计本身也是一种数据处理，保留期与访问范围要有依据。

## 六、审计的用途（不是形式主义）

| 用途 | 谁用 |
|---|---|
| **策略门复核** | D-web1 判定时参考历史 |
| **取证与溯源** | B-web2 / I-web4 补时间线 |
| **复盘** | D-web2 分析"决策慢在哪" |
| **合规举证** | D-web3 出证据包 |
| **法律配合** | I-web5 / 法务 |
| **改进检测** | G-web1 从审计里找检测盲区 |

**审计最常见的价值不是追责，是发现"我们当时的判断依据是什么"** ——
复盘时最常出现的争议是"当时为什么这么决定"，没有决策层留痕就永远说不清。
