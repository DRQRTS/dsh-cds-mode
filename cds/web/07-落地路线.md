# 落地路线（五阶段）

> **不要一次上全部 35 个人格。**
> 阶段划分的依据不是"能力多少"，而是**每个阶段独立可用、且下一阶段依赖上一阶段的产出**。

---

## 一、五阶段总览

| 阶段 | 加入 | 人数 | 能做什么 | 关键前置 |
|---|---|---|---|---|
| **一** | 晨 + B-web1 + D-web1 + D-web2 + I-web1 | 5 | 告警分诊、报告、实时防御指挥 | **D-web1 必须先就位** |
| **二** | A-web1、A-web2、B-web2、B-web5、G-web1、I-web2 | +6 | 情报、取证、检测工程、实时阻断 | 一阶段的告警流已稳定 |
| **三** | B-web3、B-web4、C-web1、C-web2、C-web3、I-web3、I-web4 | +7 | 漏洞管理、响应闭环、欺骗防御、攻击溯源 | 二阶段的取证能力已就位 |
| **四** | E 组（6 人）、D-web3、D-web4、I-web5 | +9 | 架构、合规、隐私、反击 | **D-web4 与 D-web3 先于 I-web5** |
| **五** | F 组（4 人）、G-web2、G-web3 | +6 | 攻防对抗、自动化完整体系 | 四阶段的合规与隐私已就位 |

**累计 35 个人格 + 晨。**

---

## 二、为什么是这个顺序

| 顺序决策 | 理由 |
|---|---|
| **D-web1 第一阶段就上** | 它是准入条件。**没有策略门，后面每加一个人格都是加一份风险。** |
| **D-web2 第一阶段就上** | 没有成文者，前面的产出没有出口。**报告是交付物，不是副产品。** |
| **I-web1 第一阶段就上** | 遭受攻击时没人指挥 = 谁都动或谁都不动。**指挥先于执行者。** |
| **D-web4 必须在 I-web5 之前** | 反击最容易碰到个人数据。**没有隐私否决权，反击风险不可控。** |
| **D-web3 必须在 I-web5 之前** | 反击的法律后果要有人评估。**技术能力先于合规能力是危险的。** |
| **F 组放最后** | 攻防对抗是**主动出击**能力，风险最高，且依赖前面的检测与响应能力才能形成闭环。 |
| **C 组在 B 组之后** | 没有取证就遏制 = 按感觉隔离（见 `04-证据与置信度.md` 的三级分级）。 |
| **E 组（架构）在第三阶段之后** | 架构改进需要先知道**实际被打成什么样**。第一阶段就上架构师会做出脱离实际的方案。 |

---

## 三、各阶段的进入条件与验收

### 阶段一 · 最小可用（告警分诊 + 报告 + 实时指挥）

**进入条件**：
- `.cds/authorization.md` 已建立且逐项可核对
- 用户理解"只给权限"的角色（不参与操作与判断）

**验收**：
- [ ] 一条告警进来，B-web1 能给出**分级 + 依据 + 下一位责任人**
- [ ] D-web1 能对至少 3 类动作给出**三种判定**（允许/需审批/拒绝）
- [ ] D-web2 能出一份**不看前置文档也能读懂**的报告
- [ ] I-web1 能在 5 分钟内给出**态势三句话**
- [ ] 审计落盘可用（`.cds/audit.md` 字段齐全）

**不做的事**：本阶段**不具备主动响应能力**（没有 C-web1）。响应只能靠人工，或等第二阶段。

---

### 阶段二 · 看得清（情报 + 取证 + 检测工程 + 实时阻断）

**进入条件**：阶段一验收通过，且告警流稳定

**验收**：
- [ ] A-web1 能给出**带来源的资产图谱**，范围外资产单独列节
- [ ] A-web2 的 IOC 全部标了**来源数 / 置信度 / 时效**
- [ ] B-web2 的影响范围**三级分列**，攻击链标了 `gap`
- [ ] B-web5 的 C2 判定给了**三个特征**
- [ ] G-web1 的每条规则都有**回放误报率**
- [ ] I-web2 的阻断**没有跳档**，且封禁前查了业务归属

---

### 阶段三 · 控得住（漏洞 + 响应闭环 + 欺骗 + 溯源）

**进入条件**：阶段二验收通过（尤其取证分级能力）

**验收**：
- [ ] S 漏洞报告有**降噪结果**（确认/未确认/误报三类计数）
- [ ] C-web3 的遏制方案有**至少三档梯度**与业务影响数字
- [ ] C-web1 执行**逐项有回滚方案**，且没扩大范围
- [ ] C-web2 的验证是**重放攻击路径**，不是复扫端口
- [ ] I-web3 蜜罐**验证过不可作跳板**
- [ ] I-web4 的归因**标了置信度**，低置信度未给组织名

---

### 阶段四 · 合规与反击（架构 + 合规 + 隐私 + 反击）

**进入条件**：
- **D-web3 与 D-web4 已就位**（反击的前置）
- 阶段三验收通过

**验收**：
- [ ] D-web3 结论**带标准号 + 条款号**
- [ ] D-web4 能行使**一票否决**并给替代路径
- [ ] I-web5 **准入七项逐项核对**，缺项拒收
- [ ] I-web5 未执行"绝对不做"清单中的任何动作
- [ ] E 组方案**有威胁模型**，纵深防御**写了单层失效后剩什么**

**重要**：本阶段 I-web5 上线后，**必须先做一次"拒收演练"** ——
故意提交一个缺用户凭据的反击请求，验证 I-web5 确实拒收。**能拒收，才算可用。**

---

### 阶段五 · 完整体系（攻防对抗 + 自动化）

**进入条件**：阶段四验收通过

**验收**：
- [ ] F-web1 测试**未越界**，额外发现走"建议扩展"
- [ ] F-web2 报告**按 ATT&CK 分阶段**，且"未发现"与"已发现"同等显著
- [ ] F-web4 的 0day 走完**处置流程**（上报/评估/缓解/披露协商/留痕）
- [ ] G-web2 自动化**有熔断三件套**且干跑过
- [ ] G-web3 工具**自身无命令注入 / 无硬编码凭据**

---

## 四、全程不变的六条

无论哪个阶段，这六条**从第一天就生效**：

| # | 规则 |
|---|---|
| 1 | **D-web1 必须独立且不可绕过** |
| 2 | **用户权限接口始终保留** |
| 3 | **晨始终对用户负责** |
| 4 | **人类只给权限**（不参与操作、判断、学习） |
| 5 | **越界即停** |
| 6 | **全程留痕** |

---

## 五、常见的落地错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 一次上全部 35 个人格 | 流程未验证，风险面直接拉满 | 按五阶段上 |
| 先上 I-web5（反击）再上 D-web3/D-web4 | **反击没有合规与隐私约束** | D-web3/D-web4 先于 I-web5 |
| 跳过 D-web1 先上执行组 | 所有动作无门禁 | D-web1 第一阶段必上 |
| 第一阶段就要主动响应能力 | 没有 C-web1，强行响应 = 越权 | 阶段一接受"只能看不能动" |
| 先上 E 组（架构） | 做出脱离实战的架构方案 | E 组放第三阶段之后 |
| 上了 F 组但没有检测能力 | 红队演练没意义（蓝队看不见） | F 组放最后 |
| 只关注"加了多少人格" | 忽略流程是否能闭环 | 按验收清单验，不按人数验 |

---

## 六、最小可用配置（如果只能上一个阶段）

**阶段一就是最小可用配置**：晨 + B-web1 + D-web1 + D-web2 + I-web1。

它能做到：
- 告警进来 → 有人分诊
- 决策要落地 → 有策略门把关
- 事件结束 → 有人成文
- 攻击正在发生 → 有人指挥（虽然执行能力有限）

**它做不到主动阻断与取证** —— 但那需要阶段二。**先用起来，再扩展。**
