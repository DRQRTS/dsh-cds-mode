# 循环失控、僵局、降级与熔断

> 本文件是 CDS 模式的**逃生舱**。它存在的意义是：让一个分工明确的多智能体班组**不会因为分工而卡死**。

> **前提**：本节所有"派发 / 唤醒"动作都服从 `CORE.md` 第六节的**角色委任协议**——
> 用 `role_ref` 指向目标人格委任书并装载（`role_load: static`，见 L8）。**只给路径且不装载 = 委任失败。**
> 降级替补同理：替补人格也要装载**它自己**那份委任书，而不是失效人格的那份。

---

## 一、熔断（Circuit Break）

### 触发条件

| 编号 | 条件 | 说明 |
|---|---|---|
| CB-1 | 连续 **5 轮** TEST→TRIAGE→BUILD→TEST 未收敛 | 标准熔断 |
| CB-2 | **连续 2 轮**（新增 S1+S2）≥ 本轮修复数 | 修复引入的问题**不比修掉的少**，连续两轮说明修法本身有问题。**计数口径**：新增 = 本轮新报的 S1/S2（含 D1 用 `REG-` 前缀标记的回归 bug，其类型码为 `T-REG-*`）；修复数 = 本轮已关闭的 bug 数 |
| CB-3 | 代码行数连续 **3 轮净增长**，且 bug 数未下降 | 越修越乱 |
| CB-4 | 用户与晨在需求上出现分歧，且**已用选择题问过 ≥ 2 轮**（每轮 ≤ 3 题）仍未收敛 | 方向性分歧。**判据是「问过几轮」，不是「感觉说不清」** —— 晨必须在 `state.json.questioning` 里留有这两轮的题面与用户选择，否则不算触发 |
| CB-5 | 预算/时间到达上限 | 资源熔断 |
| CB-6 | 同一 bug 被"修复" **3 次仍未修好** | 根因误判 |
| CB-7 | **连续 2 轮 S1/S2 = 0，但晨仍准备开新轮** | **无效轮次熔断**。判据客观：查 `state.json.bugs` 近两轮的 S1/S2。触发即**强制收口**，不需用户裁决 |

> **CB-7 是专治「吹毛求疵」的保险丝。** 前六条都假设「还有真问题要修」，
> 只有 CB-7 针对「没有真问题、但仍在挑」的情形。它是**唯一一条触发后直接收口的熔断**——
> 因为「再修一轮」在这种情况下没有任何正当理由，不需要问用户。

### 熔断动作（晨必须执行，不得跳过）

1. **立即停止所有工作流推进**，冻结当前状态，写入 `.cds/state.json` 的 `circuit_break` 字段；
2. 向用户输出**熔断报告**，格式：

```md
## 熔断报告

### 事实
- 触发条件：CB-1（连续 5 轮未收敛）
- 五轮 bug 数：S2 3→4→5→6→7，S3 9→11→10→12→13
- 累计改动：14 个文件，净增 620 行

### 我的判断
不是"再修一轮"的问题。三条 S2 全部指向同一个根因：状态管理模型与需求不匹配。
继续修只会增加补丁数量。

### 选项（三选一，我不替你选）
A. 缩小范围：把 <功能X> 从本版移除，剩余部分预计 2 轮内收敛。
   代价：<功能X> 延期。
B. 接受残余风险：S2 三条记录为 known-issue，先交付。
   代价：<具体后果，用大白话说>。
C. 回炉重设计：回到 DESIGN 节点重做状态模型。
   代价：约 <n> 轮返工，但根治。

### 我建议 A
理由：<一句话>。
```

3. **等待用户决策**。未收到决策前，除存档外不做任何改动。

## 二、僵局（Deadlock）

判定：两个或以上人格**互相要求对方先动**，或**对同一问题给出互斥结论且都不让步**。

### 常见僵局类型

| 类型 | 例子 | 仲裁人 |
|---|---|---|
| 门禁拉锯 | C 组说设计稿不完整；B4 说已收口 | **D6**（以"开发组能否无提问开工"为客观标准） |
| 结论互斥 | A1 按官方文档主张 X；A2 按既有实现主张 Y | **A4**（并列保留 + 上报用户，不裁决） |
| 审美冲突 | B1 要奇想；B2 要务实 | **B4**（裁决并记录代价，一票收口） |
| 推诿 | C2 说等 C1；C1 说等设计 | **晨**（直接指定顺序，C1 → C2 是固定次序） |
| 数据冲突 | D1 实测与 A1 文档结论不符 | **以实测为准**（A1 自己定的规则：实测通过才升级） |

### 仲裁规则

1. **仲裁必须在同一轮内完成**，不接受"下一轮再说"。
2. 仲裁结果写入 `.cds/decisions.md`：`决策 / 决策人 / 理由 / 反对意见 / 代价`。
3. 败方**不得消极执行**。若败方认为裁决会导致严重后果，可提一次书面异议（写入 decisions 的"异议"栏），但**必须照裁决执行**。
4. 仲裁人自身不可用时，按 `CORE.md` 第八节的同构降级规则替换。

### 死锁保险丝

若同一僵局在 **2 轮内**被重复触发，说明**结构本身有问题**，转为 CB-4 熔断处理。

## 三、降级（Degradation）

### 人格降级映射

| 失效人格 | 降级替补 | 能力缺口（必须写入 decisions） |
|---|---|---|
| A1 | A2 | 官方资料批判性下降，需额外实测 |
| A2 | A1 | 复用调查能力下降，倾向自研，成本上升 |
| A3 | B1 | 个性化调查转为设计阶段产生，缺少外部资料佐证 |
| A4 | A1 | 汇总能力下降，产物结构可能不统一 |
| B1 | A3 | 奇想来源转向外部资料 |
| B2 | B4 | 务实审查可能被"精进"心态稀释，需 B4 自觉 |
| B3 | B2（视觉基线以既有项目为准） | 审美判断退化，需更多用户确认 |
| B4 | **不可降级** | 收口权必须存在。B4 不可用则**暂停流程并报告用户** |
| C1 | C3 | 前端产能下降 |
| C2 | C3 | 后端产能下降 |
| C3 | C1 或 C2 | 细节与回归守卫能力下降，风险显著上升，需 D1 加强 |
| C4 | **不可降级** | 安全层不可由非专职人格顶替；C4 不可用则**该版本标记为"未做安全层"并必须告知用户** |
| D1 | D2 | 代码级覆盖下降 |
| D2 | D1 | 体验类 bug 可能漏检 |
| D3 | D1 | 长远 bug 覆盖下降 |
| D4 | B3 | AI 味治理转入设计侧，检测能力下降 |
| D5 | C4（仅做自查，非盲测） | **盲测假设被破坏，结论置信度降为"低"**，必须在报告中声明 |
| D6 | B4 | 分类汇总合并到设计组，注意保持分类法结构 |

**降级纪律**：
- 降级必须**显式记录**，不得静默；
- 降级后的产物必须**标注降级状态**，避免下游误信其完整性；
- **B4 与 C4 是唯二不可降级人格**。原因：分别是"收敛阀"与"安全底线"。

### 流程降级（项目规模裁剪）

见 `workflow/01-new-project.md` 末尾的「复杂度调节」表。规则：**跳过谁必须记录，不得静默跳过**。

## 四、需求侧异常处理

| 异常 | 处理 |
|---|---|
| 用户回答自相矛盾 | 晨不用判断题，改用**具体场景选择题**（"如果有用户同时做 A 和 B，你希望结果是 1 还是 2？"） |
| 用户说"你决定" | 记录 `delegated`；B 组给方案、晨给默认值；在 `decisions.md` 标注「用户授权代理决策」，并在交付报告里**显式列出代决策项** |
| 用户中途改变主意 | 不影响已完成的调研（资料仍有效）；设计稿需**重新收口**；已写代码保留但不删除，标注 `@deprecated-by-decision` |
| 用户要求与安全冲突 | C4 拒绝 → 上报晨 → 晨向用户说明具体攻击场景与后果 → 由用户书面确认后才可执行，且必须在 `decisions.md` 留痕 |
| 用户要求与法律/许可冲突 | 触发 E7（若不存在则由 A1 查法条/许可证）→ 晨明确告知风险 → 用户确认后留痕 |
| 用户长时间不回复 | 不推进。将当前状态写入 `state.md` 并在下次对话开头一句话复述上下文（**不重述全部历史**，省钱） |

## 五、成本熔断（与自救模式联动）

### 5.1 预算为主，熔断为辅（**重要**）

**早先只有熔断（事后刹车），没有预算（事前刹车）。** 这是「30 分钟的活用 2 小时」的制度成因：
熔断要到连续 5 轮不收敛才踩，而一个本该 1 轮的活可以合法地跑满 5 轮才被拦下。

| 机制 | 性质 | 触发点 | 动作 |
|---|---|---|---|
| **预算** | **事前** | 开工时定下（规模闸门） | 用尽即交付，残余转 known-issue |
| **熔断** | **事后** | 连续 5 轮未收敛 | 停下，三选一报告用户 |

**两个都要有。** 只有熔断 = 允许你花光 5 轮才发现方向不对；只有预算 = 遇到真僵局时不知道怎么退。

### 5.2 预算对账（每轮结束，晨执行）

```
轮次已用 / rounds_cap → 剩余轮次
提问已用 / question_cap → 剩余题量
```

| 情形 | 动作 |
|---|---|
| 剩余轮次 = 0，未收敛 | **交付**（正常收口，不是失败），残余转 known-issue |
| 剩余轮次 = 1 | 提前告知用户「这是预算内最后一轮」，本轮**只修 S1/S2** |
| 提问超预算 | 停止提问，剩余项按默认值推进并标注代决策 |
| 实际轮次 > 预算 × 1.0 | 写 `overrun_reason`；**未写理由 = 违规** |

### 5.3 成本警报表

| 警报 | 信号 | 动作 |
|---|---|---|
| 上下文膨胀 | 单次调用携带的上下文超出必要（含大量已落盘资料全文） | 立即改为**只传路径**（见 `selfrescue/cache-economy.md`） |
| 缓存失效 | 系统段频繁变动导致前缀不稳定 | A4/B4 检查是否有动态插值混入前缀 |
| 重复调研 | 同一问题被不同人格重复调查 | D6 在汇总时标记，下一次任务里合并 |
| 人格空转 | 某人格被调用但无实质产出 | 晨在下一轮取消该人格调用并记录 |
| **无效轮次** | 本轮 S1/S2 = 0 却仍开了修复轮 | **立即收口**，不再开轮；记入轮次成本台账 |
| **超编派发** | 派了规模表外的人格且无理由 | 下轮收回编制；补写理由到 `decisions.md` |
| **重复复测** | 重测上轮已过、代码未动的视角 | 下轮改用「按变更范围定复测范围」表 |
| **串行等待** | 独立任务被拆成多次派发 | 改为同批并发 |

**成本熔断的判定权归晨**，但**执行建议权归 A4 与 D6**（他们看全局产物）。

## 六、流程自检（每轮结束，晨执行）

**A. 收敛与质量**

- [ ] 当前轮次的 bug 净变化是多少？
- [ ] **S1/S2 各几个？** 是不是 0？
- [ ] **如果 S1/S2 = 0，我为什么还要开下一轮？**（答案涉及 S3+ → **停，收口**）
- [ ] 有没有触发熔断条件？（含 **CB-7 无效轮次**）
- [ ] 有没有未记录的降级？
- [ ] 有没有 Frozen List 项被动过？
- [ ] `decisions.md` 是否覆盖了本轮所有关键决策？
- [ ] `state.json` 与 `state.md` 是否一致？
- [ ] 本轮传递的是路径还是全文？
- [ ] 有没有人格在空转？

**B. 预算与编制（新增）**

- [ ] 规模定下了吗？我按规模表派的人吗？
- [ ] 剩余轮次还有几轮？预算对账写了吗？
- [ ] 有没有超编派发？有理由吗？
- [ ] 该并行的是否真并行了？有没有串行等待？
- [ ] 复测范围是按「变更范围表」定的，还是无脑重跑全部视角？
- [ ] 轮次成本台账更新了吗？本轮是不是无效轮次？
