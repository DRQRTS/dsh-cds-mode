# 工作流二：接手已有项目

> 适用：存在既有代码、用户给出仓库/目录、用户说「接手 / 维护 / 接着做 / 改一下这个」。
> 与工作流一的核心差异：**先盘点现状，再谈需求**；**默认不推翻既有风格**；**回归测试优先于新功能**。

---

## 差异总表

| 环节 | 新项目 | 接手项目 |
|---|---|---|
| 首次提问 | 前 5 题校准 + 70–280 题需求 | 前 5 题校准 + **现状盘点简报** + 接手意图 5–10 题 |
| 调研重心 | 该怎么做 | **它现在是怎么做的、为什么这么做**（A2 主导） |
| 设计前提 | 自由设计 | 受既有约定约束，**先出「不可动清单」** |
| 开发前提 | 从零写 | 增量修改，**C3 守卫既有逻辑** |
| 测试前提 | 测新功能 | 先建**回归基线**，再测新功能 |
| 风险重心 | 做不出来 | **改坏了原有能用的东西** |

---

## 阶段 0 · 校准（CALIBRATE）

同工作流一。前 5 题增加两题变体（见 `questions/00-calibration.md` 的接手版）：

- 这个项目是你写的吗？
- 你能接受改动的最大范围是什么？（只改需求 / 可改实现 / 可改架构 / 可重写）

第二题的答案直接决定后续**授权半径**，必须写入 `.cds/state.json`：

| 授权半径 | 含义 | 对工作流的约束 |
|---|---|---|
| `R0 只加不改` | 不许动任何既有文件的行为 | 新功能只能新增文件/新增入口 |
| `R1 可改实现` | 可改内部实现，接口契约不变 | C3 必须守接口 |
| `R2 可改架构` | 可调整模块划分与接口 | 需在 TRIAGE 里单列架构变更计划 |
| `R3 可重写` | 允许重写 | 仍需先出「保留清单」，说明哪些旧行为必须等价保留 |

---

## 阶段 1 · 现状盘点（INVENTORY）

**执行者**：晨（访谈） + A2（代码逆向调查） + C3（可行性观察）

### 1.1 晨向用户提「接手意图」5–10 题

必问：
1. 你接手的目标是什么？（修 bug / 加功能 / 优化性能 / 现代化 / 只维护不开发）
2. 这个项目现在**能用吗**？能用到什么程度？
3. 有没有**已经踩过的坑**、已知的坑、明确不要碰的东西？
4. 你希望这次接手后，多久之内看到什么结果？
5. 有没有文档？（有/没有/过时）
6. 谁在用？出问题谁受影响？
7. 有没有测试、CI、部署脚本？
8. 授权半径（R0–R3）确认。
9. 有预算/时间上限吗？
10. 如果只能在"修好一个旧 bug"和"加一个新功能"里选一个，你选哪个？

### 1.2 A2 执行代码逆向调查（不等用户回答完即可并行）

A2 必须产出 `research/A2-takeover-inventory.md`，内容：

```md
## 既有项目盘点
### 1. 技术栈与版本（含 lockfile 实际锁定版本）
### 2. 目录结构与模块职责（谁调用谁，画调用图）
### 3. 入口清单（可执行入口、路由、定时任务、外部触发）
### 4. 数据存储（表结构 / 文件格式 / 外部服务）+ 是否有迁移机制
### 5. 依赖清单（数量、维护活跃度、已知漏洞、许可证）
### 6. 构建与运行方式（能否跑起来？跑起来的步骤？）
### 7. 现有测试（有没有、覆盖率、能不能跑）
### 8. 代码债务标记（TODO/FIXME/HACK 数量与位置；重复代码区块）
### 9. 既有约定（命名风格、错误处理风格、日志风格、注释风格）
### 10. 明显缺陷与安全隐患（只列现象，不下结论）
### 11. 未知与无法判断的部分（明确列出）
```

**特别要求**：
- **能跑就跑起来**。跑不起来的项目，第一优先级是"让它跑起来"，不要急着改代码。
- 记录**实际锁定版本**，不是 `package.json` 里写的版本范围。
- 已知漏洞排查必须做（与 C4 联动）。

### 1.3 C3 提供可行性观察

C3 只做一件事：判断**现有代码是否具备被安全修改的条件**（有无测试、有无构建、有无类型、耦合程度）。
产出：`research/C3-modifiability.md`

### 1.4 晨产出「不可动清单」

晨将 1.1–1.3 汇总，与用户确认一份**不可动清单（Frozen List）**：

```md
## 不可动清单（用户确认版）
- F-01: <路径或行为> —— 理由：<用户理由> —— 授权：<R0>
- F-02: ...
## 可动清单
- M-01: ...
```

**门禁**：用户未确认不可动清单，不得进入阶段 2。
**产物**：`.cds/frozen-list.md`

## 阶段 2 · 需求澄清（CLARIFY，5–10 题）

用 `questions/03-followup-10.md` 的接手版模板。此时晨已经知道现状，问题要更具体：

- 例子：「你现在这个 `list` 接口一次返回全部数据，我加筛选是在前端做还是后端做？前端做省事但数据量大时会卡。」

**产物**：`.cds/requirement.md`（追加，不覆盖原内容）

## 阶段 3 · 调研（RESEARCH）

| 人格 | 接手场景下的具体任务 |
|---|---|
| A1 | 既有技术栈的官方文档现行建议；既有 API 是否已废弃；上游已知 bug |
| A2 | **主导**：复用调查 + 盘点（见阶段 1）+ 依赖健康度 |
| A3 | 既有代码的「AI 味 / 平庸」诊断 + 个性化改造机会（**须标注是否触碰 Frozen List**） |
| A4 | 整合为 `research/00-整合资料.md`，**额外增加一节「既有实现 vs 需求差距表」** |

**A4 门禁追加**：差距表必须区分三类——
- `已有可复用`（直接调用）
- `已有需改造`（改哪里、代价）
- `完全没有`（需新写）

**产物**：`research/00-整合资料.md`

## 阶段 4 · 设计（DESIGN）

**关键原则：增量设计，不推翻既有风格。**

B 组在接手场景下的追加约束：
1. **风格一致性优先于个人偏好**。B1 的奇想若与既有风格冲突，必须标注"这是一次风格转向"，由用户决定是否接受。
2. B2 必须先回答：**这次改动会不会让老用户困惑？**
3. B3 必须先读取既有视觉资产/文案风格，产出「风格基线卡」，新设计须落在基线内（除非用户授权转向）。
4. B4 汇总时**必须新增两节**：
   ```
   ## 与既有代码的接口对照（逐文件：改哪个、新增哪个、不动哪个）
   ## 迁移与兼容（数据迁移？旧接口保留？废弃计划？）
   ```

**版本规则提醒**：接手后如果用户只是提具体要求，属于「功能问题处理」；只有明确说要升版本/重构，才走 `workflow/03-iteration.md`。

**产物**：`design/00-设计初稿.md`（首版）、`design/01-增量设计.md`

## 阶段 5 · 开发（BUILD）

```yaml
- to: C1  # 前端增量改；必须先读既有前端约定
- to: C2  # 后端增量改；必须先读既有后端约定与数据模型
- to: C3  # 双重职责：修细节 bug + 守既有逻辑（回归守卫）
- to: C4  # 安全层：先审计既有，再补新增
```

**C3 的双重职责（接手场景特有）**：
1. 建立**行为快照**：在改动前记录关键入口的输入输出（可用最小脚本或手工记录）；
2. 改动后逐一比对，任何**非预期差异**都算回归 bug，立即上报；
3. 回归 bug 与普通 bug 分开编号（前缀 `REG-`）。

**C4 追加职责**：接手项目必然带着历史安全问题。C4 产出 `security-report.md` 分两部分：
- **继承问题**（不是这次改出来的，但存在）；
- **新增问题**（本次改动引入）。
两者修复优先级不同，不得混淆。

**产物**：`src/`、`build-report.md`、`security-report.md`、`.cds/behavior-snapshot/`

## 阶段 6 · 测试（TEST）

**接手场景特有：先建回归基线，再测新功能。**

| 人格 | 追加任务 |
|---|---|
| D1 | 先跑通全部既有入口，建立**基线输出**；再测新增 |
| D2 | 对比改动前后的实机体验，找「原来能用现在不能」的退化 |
| D3 | 在此基础上追加：**这次改动 3 个月后会加速腐坏哪一块？** |
| D4 | 重点抓「新增代码与既有代码风格不一致」产生的 AI 味 |
| D5 | 盲测既有 + 新增的全部攻击面 |
| D6 | 单列 **回归类（`REG-`）** 视图，与新增 bug 分开统计 |

**产物**：`tests/00-bug-summary-<轮次>.md`（含回归专节）

---

## 阶段 7 · 归因 / 方案 / 修复 / 复测

同工作流一阶段 6–8。追加约束：

- **B4 的三合一方案**在接手场景下增加第四项：**偿还技术债的取舍**（哪些债这次还、哪些继续欠、为什么）；
- **修复必须最小化**：能改 3 行不重写文件（C 组懒惰特质在此处价值最高）；
- **每轮结束更新 `frozen-list.md`**：若某条 Frozen 项必须解冻，晨必须回头向用户重新确认，不得自行解冻。

---

## 阶段 8 · 收敛与交付

同工作流一。交付报告追加两节：

```
8. 与接手前的差异（改了什么、没改什么、为什么）
9. 仍然欠着的债（技术债 / 未解冻项 / 未验证项）
```

---

## 接手项目的红线

1. **不解冻不打招呼**：Frozen List 里的任何一项，改动前必须重新获得用户确认。
2. **不静默重写**：不允许"顺手把整个文件重写了"而不在报告里注明。
3. **不删既有测试**：测试失败要修代码或修测试并说明，不许直接删。
4. **不动用户数据**：任何数据迁移必须先备份，并给回滚方案。
5. **不假设前任的意图**：所有"我觉得他是想……"一律改为"需要确认的问题"。
6. **跑不起来先修跑起来**：接手项目第一优先级永远是「可运行」，不是「可维护」。
