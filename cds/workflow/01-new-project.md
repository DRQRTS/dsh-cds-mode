# 工作流一：新项目

> 适用：工作区为空、无既有代码、用户明确说"做个新的"。
> 循环终点：**项目不再出现 bug**（收敛判定见 `CORE.md` 第五节）。

---

## 阶段 0 · 校准（CALIBRATE）

**执行者**：晨
**输入**：无
**动作**：提 **前 5 题**（`questions/00-calibration.md`）

判定档位：

| 档位 | 判据 | 后续表述策略 | 题量 |
|---|---|---|---|
| L1 零基础 | 不知道技术栈是什么、没有写过代码 | 大白话 + 类比 + 多选项 | 70–110 |
| L2 使用者 | 用过同类产品，懂概念不懂实现 | 半通俗，术语加一句解释 | 110–170 |
| L3 开发者 | 会写代码，能讨论技术方案 | 术语直给，跳过常识题 | 150–220 |
| L4 架构决策者 | 关心取舍、成本、长期维护 | 只问决策与约束，不问实现细节 | 170–280 |

### 规模闸门（**强制，先于档位**）

> **这一格是 CDS 最容易出事的地方。** 早先的做法是：先按档位问完 70–280 题，再进全流程，
> 到最后一页才看到「复杂度调节」表——于是「写个一次性脚本」也走完了 A1–A4 + B1–B4 + C1–C4 + D1–D6。
> 结果是 30 分钟的活用掉 2 小时，产出与快车道并无差别。
>
> **规模不是最后一个问题，是第一个问题。** 它决定后面派几个人、跑几轮、花多少预算。

**动作**：在提前 5 题**之前**（或与第 1 题合并），用手上的信息先判规模。判不出来的，直接问：

```
ask_user_question(
  "这件事大概多大？",
  [
    "几分钟就完的小事（改个配置、写个一次性脚本、查个东西）",
    "半天内能收的小工具 / 单页 / 插件",
    "一个完整应用",
    "要对外发布的产品"
  ]
)
```

| 规模 | 判据 | 人格编制 | 轮次预算 | 提问量 | 预估耗时 |
|---|---|---|---|---|---|
| **极小** | 单文件脚本 / 一次性任务 / 改配置 / 问答式交付 | 最少 3 人：A2 → B4 → C(1 或 3) → D1 | **≤ 1 轮** | 3–8 题 | 分钟级 |
| **小** | 单页工具 / 插件 / 小脚本集 | A1+A2 → B2+B4 → C1+C3 → D1+D4 | **≤ 2 轮** | 10–30 题 | 半小时级 |
| **中** | 完整应用 | 全员（E 按需） | ≤ 5 轮 | 70–150 题 | 小时级 |
| **大** | 对外产品 | 全员 + E 组必选 | ≤ 5 轮 | 150–280 题 | 天级 |

**门禁**：档位与规模**均未定**，不得进入阶段 1。规模写入 `.cds/state.json` 的 `budget.scale`。

**规模可升不可降**：若过程中发现判小了（例如「一次性脚本」其实要长期维护），
**升档必须写 `decisions.md`** 并告知用户「这件事比你以为的大，我要多派几个人」。
不许静默升档，也不许为了省事把大活按小活做。

### 快车道（极小 / 小 规模专用）

极小与小的项目**不走阶段 2–9 的完整循环**，走这条：

```
CALIBRATE（含规模闸门）
   ↓
CLARIFY（3–8 题，只问「不问你就会猜错」的）
   ↓
B4 直接出方案（跳过 A 组调研——用户自己就是最好的资料源）
   ↓
C 组实现
   ↓
D1 跑一遍 + D4 扫 AI 味
   ↓
晨交付
```

**快车道的三条硬规矩**：
1. **不许派 A 组做外部调研**。极小任务的「调研」就是问用户一句或读一眼现有代码。开三个调查子代理是纯浪费。
2. **不许进收敛循环**。修一轮就交付，残余问题列 known-issue。极小任务没有「连续两轮净变化」可言。
3. **D2/D3/D5 一律不派**。极小任务没有「实机体验」「三个月后」「攻击面」三个维度可言——
   一个改配置的活不存在安全红队靶场。

> **判断口诀**：如果一句话能说清做完是什么样，就是极小；如果这篇文章的主要产物是「一个能用的东西」而不是「一套说法」，别开调查组。

**产物**：写入 `.cds/state.json` 的 `calibration.level` 与 `budget.scale`。

## 阶段 0.5 · 预算（BUDGET）

**执行者**：晨
**动作**：按规模闸门的结论写下本轮预算，之后**所有派发都要对账**。

```json
"budget": {
  "scale": "小",
  "rounds_cap": 2,
  "question_cap": 30,
  "personas_allowed": ["A1","A2","B2","B4","C1","C3","D1","D4"],
  "wall_clock_estimate": "约 40 分钟",
  "per_task_timeout_hint": "本轮预算墙钟的 1/2",
  "batch_timeout_hint": "本轮预算墙钟",
  "spent_rounds": 0,
  "spent_questions": 0,
  "overrun_reason": null
}
```

**对账规则**（每轮结束，晨执行）：

| 情形 | 动作 |
|---|---|
| 已用轮次 == `rounds_cap`，且未收敛 | **不再开新轮**。直接按「严重度分级止损」交付（见 `CORE.md` 第五节） |
| 已用轮次 == `rounds_cap` - 1 | 提前告知用户「这是预算内最后一轮了」 |
| 已用提问数 > `question_cap` | 停止提问，剩余项按默认值推进并标注为代决策 |
| 派了 `personas_allowed` 之外的人格 | 必须在 `decisions.md` 写理由；无理由 = 违规派发 |

**为什么要有预算**：光有「事后熔断」（连续 5 轮不收敛才停）是不够的——
它允许你花掉 5 轮才发现方向不对。预算是**事前**的：它先把「这件事该花多少」定下来，
超了就停，而不是等第 5 轮。

### 超时对账（**轮内**，不是轮末）

**预算的计量单位是「轮」，但卡死发生在「轮内」**——一个 A1 卡 40 分钟，整批 8 个都在等它，而预算制对此完全无感。因此除轮预算外，另设两个**墙钟阈值**：

| 阈值 | 默认 | 触发后的动作 |
|---|---|---|
| `per_task_timeout_hint` | 本轮预算墙钟的 **1/2** | 标记该实例 `partial`，**不等它**；按 `04-escalation.md` 的降级映射替补，或把该项落到下一轮 |
| `batch_timeout_hint` | 本轮预算墙钟 | **先收已回来的**，未回者一律标 `partial`，用已回收的产物推进；在报告里显式列出「谁超时、缺什么」 |

**三条纪律**：
1. **超时不是失败，是信息**——`partial` 产物照样进汇总，但要注明缺口与置信度（`protocol/bug-taxonomy.md` 的 `confidence` 字段）。
2. **绝不为了等一个慢实例而冻结整批**——那正是「预算无感、墙钟失控」的来源。
3. 超时替补**同样要走委任协议**（`role_load`），替补人格拿到的是**它自己**那份委任书。

**预算不是硬墙，是刹车**：超预算时晨必须先问用户「继续还是收口」，不许默默接着跑。

## 阶段 1 · 需求采集（CLARIFY）

**执行者**：晨
**动作**：从 `questions/01-new-project-280.md` 中按「项目类型 + 专业度档位 + **规模**」抽取题目，分批给用户（每批 ≤5 题）。

**题量由规模决定，不由档位单独决定**（见阶段 0 规模闸门）：极小 3–8 题 / 小 10–30 / 中 70–150 / 大 150–280。
档位只决定**怎么问**（表述策略），规模决定**问多少**。

> **早先的错误**：题量表只挂在档位上，于是「L3 开发者」无论做什么都会被问 150–220 题。
> 一个 L3 用户要个一次性脚本，被问了 150 题——这就是「30 分钟的活用了 2 小时」的头号成因。
> **专业度不等于规模。** 高手做小事，该问的更少，不是更多。

**提问域必须覆盖全部九类**（不得只问技术），但**每类的题量可压到 0–2 题**——
规模小的时候，很多域只需要一句话确认：

1. **身份**：项目名称、副标题、代号、是否对外可见、域名
2. **内容与功能**：做什么、给谁用、核心动作清单、明确不做的事
3. **商业性质**：免费/付费/订阅/一次性/内部工具/开源/非营利；是否要收款、发票、退款
4. **使用范围与规模**：个人/团队/公司/公众；预期用户数、数据量、并发量
5. **国家与地区**：部署地、用户所在地、是否跨国、时区、数据驻留要求
6. **语言与本地化**：界面语言、内容语言、是否多语言、是否需要 RTL
7. **开源与许可**：是否开源、许可证类型、是否允许商用、第三方代码合规
8. **技术与约束**：技术栈偏好、必须兼容的平台、必须集成的外部系统、预算、时间、维护者
9. **验收与成功标准**：怎么算做完、怎么算做好、谁验收、上线后谁维护

**规模 ≤ 小 时的九域压缩法**：不问 9×N 题，而是**一次问一组**，把不适用的整域用一句带过：

```
ask_user_question 一次给 4–5 个选项组，让用户一次勾完，而不是一道一道来。
例如第 3/4/5 域可以合并成：「这东西给谁用？（就我自己 / 团队内部 / 公开）」
                          「放哪跑？（我电脑上 / 公司内网 / 公网）」
——用户答这两句，商业性质/规模/地区三域的默认值就都定了。
```

**收尾动作**（必做）：
1. 输出一份**需求摘要**（极小 ≤150 字 / 小 ≤300 字 / 中大 ≤500 字，编号 R-001…R-xxx）；
2. 列出**所有矛盾点**，让用户裁决（≤3 题，选择题）；
3. 请用户确认摘要。用户确认后写入 `.cds/requirement.md`。

**门禁**：用户未确认需求摘要，不得进入阶段 2。
**产物**：`.cds/requirement.md`

## 阶段 2 · 调研（RESEARCH）

**执行者**：A1 → A2 → A3 → A4（A1–A3 可并行）

```yaml
# 并行派发（每个 to 都按 CORE.md 第六节 6.1 锚定委任书：role_ref + role_load；
# 同编号多轮复用走 role_load=static，首次/低频走 role_load=inline）
- to: A1  # 官方资料 + 民间说法验证   role_ref: personas/A1-官方派调查者.md   role_load: static
- to: A2  # 复用与选型              role_ref: personas/A2-复用派调查者.md   role_load: static
- to: A3  # 个性化与去 AI 味         role_ref: personas/A3-个性化派调查者.md   role_load: static
# 三者完成后（A4 可并行读取三份，整合时按 A1→A2→A3 顺序呈现）
- to: A4  role_ref: personas/A4-汇总验证者.md   role_load: static
```

> **只写 `to: A1` 不等于委任。** 必须确保 `personas/A1-官方派调查者.md` 的内容**真正进入子 Agent 的角色定义**（CORE 铁律 L8）——走静态区一次装载，或首次内联。
> **只写路径、不管卡片有没有被读 = 委任失败**；但每次派发都重新粘全文同样违规（违反 `cache-economy.md`「全文搬运次数 = 0」）。

**输入**：`.cds/requirement.md`
**A4 门禁**：需求映射表覆盖 100% 需求项；冲突项并列保留；无「我觉得」句式。
**产物**：`research/A1-official.md`、`research/A2-reuse.md`、`research/A3-individual.md` → `research/00-整合资料.md`

## 阶段 3 · 设计（DESIGN）

**执行者**：B1 / B2 / B3 → B4

**注意（重要）**：本阶段产出的是**首个版本的完整开发流程设计**，必须**非常详尽**。后续用户要求更新/重构/变更版本号时，才设计下一个版本的完整流程（见 `workflow/03-iteration.md`）。

```yaml
- to: [B1, B2, B3]   # 并行，各自出方案（含代价）
- to: B4             # 汇总 + 强制收口
```

**B4 收口门禁**（硬性，见 `personas/group-b-design.md`）：
- 所有需求项有落点（含「明确不做」+ 理由）；
- 无未指派人的待定项；
- 每个设计决定都写了代价；
- B1/B2/B3 的反対意见均已裁决或记录；
- **开发组可在不问任何问题的情况下开工**。

**产物**：`design/00-设计初稿.md`

## 阶段 4 · 开发（BUILD）

**执行者**：C1 → C2 → C3 → C4（**顺序敏感**：先前端，再后端）

```yaml
- to: C1   # 前端（附校准记录）
- to: C2   # 后端；动手前必须向 C1 提结构化问题（protocol/peer-channel.md）
- to: C3   # 概览 + 跑一遍 + 修非重构性 bug
- to: C4   # 安全层（12 项标准化清单）
```

**C2 强制动作**：删除前端 mock/示例内容，替换为实际功能。
**C3 强制动作**：交付前模拟执行路径，报告执行轨迹。
**C4 强制动作**：交付「红队入口说明」给 D5（不含源码）。

**门禁（按规模分级）**：
- **极小 / 小**：可运行产物 + `build-report.md`，其中含一节「安全自检（非 C4 级）」并**声明置信度**。
- **中 / 大**：上述 + `security-report.md`（C4 安全层报告，**硬性，不可省**）。

> **为什么分级**：极小/小的编制表里**本来就没有 C4**（见阶段 0 规模闸门）。若门禁一律要 C4 报告，快车道**永远过不了 BUILD 门禁**，只能靠"标记未做"绕过——那门禁就形同虚设。反过来，为过门禁硬派 C4，正是阶段 0 批判的「极小任务派安全层」的浪费。

**产物**：`src/`、`build-report.md`、（中/大另加）`security-report.md`、`tests/D5-redteam-entry.md`

## 阶段 5 · 测试（TEST）

**执行者**：按规模派 D 组（见下表），→ D6（必须等被派的人全回来）

| 人格 | 测试视角 | 输入 | 极小 | 小 | 中 | 大 |
|---|---|---|---|---|---|---|
| D1 | 代码从上到下跑一遍 | 源码 + 入口 | **必派** | **必派** | **必派** | **必派** |
| D2 | 实机体验、视觉与操作协调 | 运行环境 | — | — | **必派** | **必派** |
| D3 | 「三个月后会出什么问题」 | 源码 + 部署形态 | — | — | 按需 | **必派** |
| D4 | AI 味（代码 + 文本 + 设计） | 全产物 | **必派** | **必派** | **必派** | **必派** |
| D5 | 安全红队（**不给源码**） | 红队入口说明 | — | — | 有对外接口时**必派** | **必派** |

> **「必派」的原意被误用了。** 这张表早先五格全写「必派」，理由是「只派 D1 等于只测了五分之一」。
> 那句话本身没错——五个视角测的确实是不同的东西。**但它回答的是「派了就要派全」，
> 不是「任何项目都必须五个都派」。** 一个改配置的活没有「三个月后」可言，一个本地脚本没有攻击面可言。
>
> **正确理解**：五个视角之间不可互相替代（所以要么不派，派了就要真派到位）；
> **但派不派，由项目规模决定**。极小/小项目砍掉不相干的视角，是**正确的裁剪**，不是偷懒。

> **这一格最容易做错**：只派 D1 就等于**在保留了 D1 的项目里只测了五分之一**。
> 所以：一旦决定做「实机体验」这一维，就必须真派 D2，不许用 D1 的结论冒充。
> 反过来说，极小项目本来就不做「实机体验」这一维——那不算漏测。

**并发派发**：同一轮内被派到的 D 人格**必须同批并发**，不许串行（它们前置输入互不依赖）。

> **一个例外：D5 不在这一批里。** D5 的输入**物理上来自 C4**（`tests/D5-redteam-entry.md` 由 C4 在 BUILD 阶段末尾产出），与 D1–D4 的输入（源码 / 运行环境 / 全产物）**无交集**。
> 把 D5 画进 D1–D4 同一批，要么它拿到空文件白跑，要么整批为等 C4 而拖慢 D1–D4。
> **正确做法**：`D1–D4` 同批并行；**D5 单列**，在 C4 交付红队入口后单独派 → 它是一条 `C4 ──> D5` 的独立边。

**D6 门禁**：去重合并、等级校准、交叉印证、净变化统计齐备。**D6 必须等本轮被派的人全部回来**。
**产物**：`tests/bugs-D1..D5-<轮次>.md` → `tests/00-bug-summary-<轮次>.md`

### 复测范围收敛（**重要，治「越测越久」**）

**复测必须包含上一轮的遗留 bug 与回归项**——但**不必重跑全部视角**。规则：

| 上一轮改了什么 | 本轮复测派谁 |
|---|---|
| 只改了某模块的实现细节 | 派**当初发现问题的那个视角** + D1 跑回归 |
| 改了接口 / 数据流 | 派 D1 + D2（行为与体验都可能变） |
| 改了安全相关代码 | 派 D5 复测（原视角） + D1 |
| 只是文档 / 注释 / 文案 | **只派 D4**，不重跑 D1/D2/D5 |

**禁止**：每轮无脑重跑全部视角。那是**成本翻倍而信息量不变**——
上一轮已经通过的视角，在没被触碰的代码上重测一遍，结论必然相同。

## 阶段 6 · 归因与方案（TRIAGE）

**执行者**：D6 → A 组（找原因）→ B4（出方案）→ 晨（必要时问用户）

**串行三步，A1/A2 同批**：

```
D6（汇总定位）─┬─> A1 ┐
               └─> A2 ┘  同批并行 ──> A4（归因汇总）──> B4（出方案）
```

**A1 与 A2 必须在同一批里一次派完**：两者输入同为 D6 那份归因任务清单、彼此无产物依赖，按 CORE 6.3「没有产物依赖就是独立」判据**本就该并行**。规定串行等于每轮白等一个 A 组人格的完整往返。

```yaml
# 第一批（同批并发）：两条独立归因线
- to: A2  # 依据 bug 报告逆向调查：是选型问题？复用失误？
- to: A1  # 官方文档层面：该行为是否为规范允许？上游是否已知问题？

# 第二批（等 A1、A2 全回）：归因汇总
- to: A4

# 第三批：三合一方案
- to: B4  # 出「bug 修复方案 + 项目优化方案 + 轻量化方案」三合一
```

**D6 的归因任务清单同时交 A1 与 A2**——不先交一个、等它回来再交另一个。

**B4 必须同时产出三份内容**（这是本模式的特征要求）：
1. **修复方案**：逐 bug 的修法（不许"重写"了事）；
2. **优化方案**：借修复顺手解决的问题；
3. **轻量化方案**：**减少代码量**的机会清单（C 组的懒惰特质在此被制度化）；
   - 要求：每条给出「预计减少行数 / 删除的依赖 / 删除的文件」；
   - 若某轮无可轻量化项，必须显式写「本轮无轻量化项」+ 理由。

**若归因指向设计层结构性问题**：B4 上报晨，晨向用户给出三选一（缩小范围 / 接受残余 / 回炉重设计）。
**产物**：`design/fix-plan-<轮次>.md`

## 阶段 9 · 收敛判定

每轮结束：**D6 出数字**，**B4 独立复算**，**晨 比对**，**晨 上报**：

```yaml
D6 出数字 ─┐
           ├─ 晨比对两份；不一致 → 回炉重算，不得进入收敛判定
B4 独立复算 ┘
```

**B4 的复算不读 D6 的汇总文件**（`tests/00-bug-summary-<轮次>.md`），只读原始 `tests/bugs-<轮次>.md`。
理由：出数者与使用者同源 = **自证循环**。D6 的"等级校准"若无人复核，B4 的"判定"就只是对同一份数据的确认。

```
净变化 = 本轮新发现 - 本轮修复

可进 DONE 的条件（**同时满足前三条**）：
  1) S1、S2 级 bug 数量 = 0
  2) 连续两轮无**新增** S1/S2（不看 S3 及以下）
  3) D6 与 B4 两份数字一致（不一致则回炉，不算收敛）
  4) 用户未提出新的功能性要求
```

- 收敛 → 进入阶段 10；
- 未收敛且轮次 < 预算上限 → 回到阶段 6；
- 未收敛且轮次 == 预算上限 → **交付**，残余问题转 known-issue（见下）。

### 为什么不再要求「净变化 ≤ 0」

**这是本模式早先最要命的一条设计错误。**

原判据是「连续两轮净变化 ≤ 0 **且**无新增 S1/S2」。问题在于 `净变化` 把 S3/S4/S5 全算了进去。
而 D2/D3/D4 这类视角**总能找到新东西**——「这个间距差 2px」「这句文案还能更顺」「这个命名可以更好」。
这些新发现会让净变化永远为正，于是**永远不收敛**，一轮接一轮地挑。

结果就是用户看到的：**跑了 2 小时，效果没变。** 因为后面几轮修的全是 S3/S4——
它们被修掉之后，界面看上去和两小时前一模一样，但时间花掉了。

**新判据只看 S1/S2。** S3 及以下不再影响收敛。理由：
- S1/S2 是「不能用」「会出错」，**必修**；
- S3/S4/S5 是「可以更好」，**不影响交付**，攒着以后一起改。

### 严重度分级止损（**每轮执行，不等收敛**）

| 级别 | 定义 | 处理 | 是否阻断交付 |
|---|---|---|---|
| **S1** | 崩溃 / 数据丢失 / 安全漏洞 / 核心功能不可用 | **立即修** | **是** |
| **S2** | 主要功能异常 / 明显错误结果 / 严重体验缺陷 | **本轮修** | **是** |
| **S3** | 次要功能瑕疵 / 边界情况未处理 / 可感知但不影响使用 | **攒批**：≥3 条一起修，或用户要求时修 | 否 |
| **S4** | 体验优化 / 代码整洁 / 措辞打磨 | **只登记，不修**（除非用户点名） | 否 |
| **S5** | 个人偏好 / 见仁见智 / 「我觉得可以更好」 | **不登记**，口头提一句即可 | 否 |

**止損三条硬规矩**：

1. **修完所有 S1/S2 即认为达标**，S3 及以下不许再开新轮次。
2. **S4/S5 不许写进 bug 台账当作待办**——它们是「意见」，不是「bug」。
   台账只登记 S1–S3。S4/S5 写在交付报告的「可选改进」里，用户想改再说。
3. **D 组每轮必须显式报告 S3/S4/S5 各几条**，让晨看得见「这轮挑出来的东西有多不值钱」。
   若某轮 S1/S2 = 0 而 S3+ 有 10 条，**直接收敛**，不要为此再来一轮。

### 收敛后的强制动作

一旦满足收敛条件，**B4 必须立即宣布收口**，晨进入交付。此后：
- **禁止**任何人格对已收敛的成果提出新的 S3/S4/S5 意见并据此要求再改；
- 若确有必要改，走 `workflow/03-iteration.md` 的**版本变更**流程（需用户明确授权）；
- 收敛判定写入 `.cds/state.json` 的 `bugs.converged`。

- 收敛 → 进入阶段 10；
- 未收敛且轮次 < 5 → 回到阶段 6；
- 未收敛且轮次 ≥ 5 → **熔断**，晨停下向用户报告（`workflow/04-escalation.md`）。

## 阶段 10 · 交付（DONE）

**执行者**：晨
**前置动作（强制）**：交付前先跑一遍 `protocol/release-checklist.md` 的**七条硬勾选**，任一未勾不得进 DONE。
**交付报告结构**：
```
0. 放行清单（七条逐条勾选 + 依据坐标；未勾项写明动作或豁免理由）
1. 一句话：做完了什么
2. 怎么用（≤5 步，含启动命令）
3. 能用的部分（清单）
4. 已知问题（不藏，含等级与影响）
5. 未验证项（明确说明未验证原因）
6. 建议的下一步（≤3 条）
7. 产物索引（所有人格产物路径）
```
**同时更新**：`.cds/state.md`（人类可读）、`.cds/state.json`（机器可读）。

## 复杂度调节（按项目规模裁剪）

> **这张表早先放在本文件最后一页，是「建议」。现在它是阶段 0 的「规模闸门」，
> 是强制的第一步。** 内容与阶段 0 的编制表一致，此处保留作速查。

| 项目规模 | 人格编制 | 轮次预算 | 提问量 |
|---|---|---|---|
| **极小**（单文件脚本 / 一次性任务 / 改配置） | A2 → B4 → C1 或 C3 → D1 + D4 | **≤ 1 轮** | 3–8 |
| **小**（单页工具 / 插件 / 小脚本集） | A1 + A2 → B2 + B4 → C1 + C3 → D1 + D4 | **≤ 2 轮** | 10–30 |
| **中**（完整应用） | 全员（E 按需） | ≤ 5 轮 | 70–150 |
| **大 / 对外产品** | 全员 + E 组（E7 合规、E6 运维、E11 文档）**必选** | ≤ 5 轮 | 150–280 |

**裁剪纪律**：跳过哪个人格必须写入 `.cds/decisions.md`，注明理由与残余风险。不得静默跳过。

**反向纪律（新增）**：**不许把大活按小活做**。若在快车道执行中发现问题比预想大
（例如「一次性脚本」实际要接数据库、要长期维护），**必须升档**：停下、写 `decisions.md`、
告知用户「这件事比你以为的大，我要多派几个人」。升档需要用户点头，但**不许因为升档麻烦就硬撑**。
