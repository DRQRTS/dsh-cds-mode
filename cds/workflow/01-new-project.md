# 工作流一：新项目

> 适用：工作区为空、无既有代码、用户明确说"做个新的"。
> 循环终点：**项目不再出现 bug**（收敛判定见 `CORE.md` 第五节）。

---

## 阶段 0 · 校准（CALIBRATE）

**执行者**：晨
**输入**：无
**动作**：提 **前 5 题**（`questions/00-calibration.md`）

判定档位：

| 档位 | 判据 | 后续表述策略 | 题量 |
|---|---|---|---|
| L1 零基础 | 不知道技术栈是什么、没有写过代码 | 大白话 + 类比 + 多选项 | 70–110 |
| L2 使用者 | 用过同类产品，懂概念不懂实现 | 半通俗，术语加一句解释 | 110–170 |
| L3 开发者 | 会写代码，能讨论技术方案 | 术语直给，跳过常识题 | 150–220 |
| L4 架构决策者 | 关心取舍、成本、长期维护 | 只问决策与约束，不问实现细节 | 170–280 |

**门禁**：档位未定，不得进入阶段 1。
**产物**：写入 `.cds/state.json` 的 `calibration.level`。

---

## 阶段 1 · 需求采集（CLARIFY）

**执行者**：晨
**动作**：从 `questions/01-new-project-280.md` 中按「项目类型 + 专业度档位」抽取 **70–280 题**，分批给用户（每批 ≤5 题）。

**提问域必须覆盖全部九类**（不得只问技术）：

1. **身份**：项目名称、副标题、代号、是否对外可见、域名
2. **内容与功能**：做什么、给谁用、核心动作清单、明确不做的事
3. **商业性质**：免费/付费/订阅/一次性/内部工具/开源/非营利；是否要收款、发票、退款
4. **使用范围与规模**：个人/团队/公司/公众；预期用户数、数据量、并发量
5. **国家与地区**：部署地、用户所在地、是否跨国、时区、数据驻留要求
6. **语言与本地化**：界面语言、内容语言、是否多语言、是否需要 RTL
7. **开源与许可**：是否开源、许可证类型、是否允许商用、第三方代码合规
8. **技术与约束**：技术栈偏好、必须兼容的平台、必须集成的外部系统、预算、时间、维护者
9. **验收与成功标准**：怎么算做完、怎么算做好、谁验收、上线后谁维护

**收尾动作**（必做）：
1. 输出一份**需求摘要**（≤500 字，编号 R-001…R-xxx）；
2. 列出**所有矛盾点**，让用户裁决（≤3 题，选择题）；
3. 请用户确认摘要。用户确认后写入 `.cds/requirement.md`。

**门禁**：用户未确认需求摘要，不得进入阶段 2。
**产物**：`.cds/requirement.md`

---

## 阶段 2 · 调研（RESEARCH）

**执行者**：A1 → A2 → A3 → A4（A1–A3 可并行）

```yaml
# 并行派发（每个 to 都要按 CORE.md 第六节读该人格委任书全文，作为 role_text 传入）
- to: A1  # 官方资料 + 民间说法验证      role_text: personas/A1-官方派调查者.md 全文
- to: A2  # 复用与选型                  role_text: personas/A2-复用派调查者.md 全文
- to: A3  # 个性化与去 AI 味            role_text: personas/A3-个性化派调查者.md 全文
# 三者完成后
- to: A4  # 依次读取三份，整合为单一长文件   role_text: personas/A4-汇总验证者.md 全文
```

> **只写 `to: A1` 不等于委任。** 必须把 `personas/A1-官方派调查者.md` 的**正文**作为子 Agent 的【角色定义】段传入（CORE 铁律 L8）。只给路径 = 委任失败。

**输入**：`.cds/requirement.md`
**A4 门禁**：需求映射表覆盖 100% 需求项；冲突项并列保留；无「我觉得」句式。
**产物**：`research/A1-official.md`、`research/A2-reuse.md`、`research/A3-individual.md` → `research/00-整合资料.md`

---

## 阶段 3 · 设计（DESIGN）

**执行者**：B1 / B2 / B3 → B4

**注意（重要）**：本阶段产出的是**首个版本的完整开发流程设计**，必须**非常详尽**。后续用户要求更新/重构/变更版本号时，才设计下一个版本的完整流程（见 `workflow/03-iteration.md`）。

```yaml
- to: [B1, B2, B3]   # 并行，各自出方案（含代价）
- to: B4             # 汇总 + 强制收口
```

**B4 收口门禁**（硬性，见 `personas/group-b-design.md`）：
- 所有需求项有落点（含「明确不做」+ 理由）；
- 无未指派人的待定项；
- 每个设计决定都写了代价；
- B1/B2/B3 的反対意见均已裁决或记录；
- **开发组可在不问任何问题的情况下开工**。

**产物**：`design/00-设计初稿.md`

---

## 阶段 4 · 开发（BUILD）

**执行者**：C1 → C2 → C3 → C4（**顺序敏感**：先前端，再后端）

```yaml
- to: C1   # 前端（附校准记录）
- to: C2   # 后端；动手前必须向 C1 提结构化问题（protocol/peer-channel.md）
- to: C3   # 概览 + 跑一遍 + 修非重构性 bug
- to: C4   # 安全层（12 项标准化清单）
```

**C2 强制动作**：删除前端 mock/示例内容，替换为实际功能。
**C3 强制动作**：交付前模拟执行路径，报告执行轨迹。
**C4 强制动作**：交付「红队入口说明」给 D5（不含源码）。
**门禁**：可运行产物 + `build-report.md` + C4 安全报告齐备。
**产物**：`src/`、`build-report.md`、`security-report.md`、`tests/D5-redteam-entry.md`

---

## 阶段 5 · 测试（TEST）

**执行者**：D1 / D2 / D3 / D4 / D5 → D6（**D1–D5 五个视角必须同批一次派完**）

| 人格 | 测试视角 | 输入 | 必派？ |
|---|---|---|---|
| D1 | 代码从上到下跑一遍 | 源码 + 入口 | **必派** |
| D2 | 实机体验、视觉与操作协调 | 运行环境 | **必派** |
| D3 | 「三个月后会出什么问题」 | 源码 + 部署形态 | **必派** |
| D4 | AI 味（代码 + 文本 + 设计） | 全产物 | **必派** |
| D5 | 安全红队（**不给源码**） | 红队入口说明 | **必派**（除非本版明确不做安全层，且已告知用户） |

> **这一格最容易做错**：只派 D1 就等于**只测了五分之一**。五个视角测的是完全不同的东西（代码行为 / 人的体验 / 时间尺度 / 风格 / 攻击面），不是"同一个人多测几遍"。它们**前置输入互不依赖**，所以**必须同批并发**，不许串行。

**D6 门禁**：去重合并、等级校准、交叉印证、净变化统计齐备。**D6 必须等 D1–D5 全部回来**（它要读全部五份）。
**产物**：`tests/bugs-D1..D5-<轮次>.md` → `tests/00-bug-summary-<轮次>.md`

---

## 阶段 6 · 归因与方案（TRIAGE）

**执行者**：D6 → A 组（找原因）→ B4（出方案）→ 晨（必要时问用户）

```yaml
- to: A2  # 依据 bug 报告逆向调查：是选型问题？复用失误？
- to: A1  # 官方文档层面：该行为是否为规范允许？上游是否已知问题？
- to: A4  # 汇总归因
- to: B4  # 出「bug 修复方案 + 项目优化方案 + 轻量化方案」三合一
```

**B4 必须同时产出三份内容**（这是本模式的特征要求）：
1. **修复方案**：逐 bug 的修法（不许"重写"了事）；
2. **优化方案**：借修复顺手解决的问题；
3. **轻量化方案**：**减少代码量**的机会清单（C 组的懒惰特质在此被制度化）；
   - 要求：每条给出「预计减少行数 / 删除的依赖 / 删除的文件」；
   - 若某轮无可轻量化项，必须显式写「本轮无轻量化项」+ 理由。

**若归因指向设计层结构性问题**：B4 上报晨，晨向用户给出三选一（缩小范围 / 接受残余 / 回炉重设计）。
**产物**：`design/fix-plan-<轮次>.md`

---

## 阶段 7 · 修复（BUILD，第 n 轮）

**执行者**：C1 / C2 / C3 / C4（按 fix-plan 分工）

**C3 特别职责**：核对修复是否引入**回归**，并把回归风险写进报告。
**产物**：更新后的 `src/`、`build-report-<轮次>.md`

---

## 阶段 8 · 复测（TEST，第 n 轮）

同阶段 5。**复测必须包含上一轮的遗留 bug 与回归项**。

---

## 阶段 9 · 收敛判定

每轮结束由 **D6 出数字**、**B4 判定**、**晨 上报**：

```
净变化 = 本轮新发现 - 本轮修复
可进 DONE 的条件（同时满足）：
  1) S1、S2 级 bug 数量 = 0
  2) 连续两轮净变化 ≤ 0，且无新增 S1/S2
  3) 用户未提出新的功能性要求
```

- 收敛 → 进入阶段 10；
- 未收敛且轮次 < 5 → 回到阶段 6；
- 未收敛且轮次 ≥ 5 → **熔断**，晨停下向用户报告（`workflow/04-escalation.md`）。

---

## 阶段 10 · 交付（DONE）

**执行者**：晨
**交付报告结构**：
```
1. 一句话：做完了什么
2. 怎么用（≤5 步，含启动命令）
3. 能用的部分（清单）
4. 已知问题（不藏，含等级与影响）
5. 未验证项（明确说明未验证原因）
6. 建议的下一步（≤3 条）
7. 产物索引（所有人格产物路径）
```
**同时更新**：`.cds/state.md`（人类可读）、`.cds/state.json`（机器可读）。

## 复杂度调节（按项目规模裁剪）

| 项目规模 | 裁剪建议 |
|---|---|
| 极小（单文件脚本 / 一次性任务） | 保留 A1、A2、B2、B4、C1（或 C2）、C3、D1、D2、D6；跳过 A3、B1、B3、C4、D3、D4、D5 |
| 小（单页工具 / 插件） | 全 A 组 + B2/B3/B4 + C1/C2/C3 + D1/D2/D4/D6 |
| 中（完整应用） | 全员（E 组按需） |
| 大 / 对外产品 | 全员 + E 组（E7 合规、E6 运维、E11 文档）**必选** |

**裁剪纪律**：跳过哪个人格必须写入 `.cds/decisions.md`，注明理由与残余风险。不得静默跳过。
