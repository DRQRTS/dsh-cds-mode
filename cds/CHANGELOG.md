# CDS 模式包 · 变更记录

> 规则：**人格卡与协议文件的任何修改都会导致全局提示词缓存失效。**
> 因此修改必须**批量、一次到位**，并在本文件登记（见 `selfrescue/cache-economy.md` 规则 P4）。

## v1.7.0

**日期**：2026-10-05
**类型**：**规范缺陷修订**（堵十五处真实存在的自身矛盾 / 制度化空转，不新增能力、不做架构改动）

### 背景

v1.6.0 上线后，对全语料做了一次**双轴独立诊断**（省时轴 + 质量轴），两个互不通气的诊断各自收敛到**同一条根因**：

> **CDS 把「检查者」与「被检查者」放在了同一个上下文里**，并且**同一份事实被要求写两遍、读两遍**。

围绕这条根因，逐条 grep 核实后确定修订清单，**按收益/代价分五批落地**：

- **第一批（四条，单文件可改、代价极小）**：B1、A2、A5、C2 —— 堵住「虚假收敛 / 串行白等 / 规范自相矛盾 / 重复盘点」。
- **第二批（五条，规范改写、零新增文件）**：A1、A3、A4、B2、B6 —— 消除「把独立的东西强行串行」与「门禁与规模错配」。
- **第三批（两条）**：C1（未读计数不再驱动轮询）、B3（修 bug 引入新 bug 追踪加严）—— 消除「规则禁它、指标奖励它」与「刹车门槛过高形同虚设」。
- **第四批（三条，含两条新增小节）**：A6（超时对账）、C3（类型 owner 表）、B4（D4 复验门禁）—— 消除「轮内无计时」「盲区伪装成干净」「否决权有口无凭」。
- **第五批（一条，含唯一新增静态层文件）**：B5（放行清单）—— 消除「单一数字当放行条件」与「列出未验证项 ≠ 放行」。

C1（检查者/被检查者上下文隔离）虽为根因，但改动面大、缓存代价高，**主动暂缓**。

### 修订一 · B1：S1/S2 定级与降级必须双签，降级禁令扩到 S3

**病灶**：`protocol/bug-taxonomy.md` 允许把 S1/S2「降级」为 S3 及以下来处理。而 D 组（特质「真诚」）自己就是报告的来源——**报告人自己把自己的严重级降掉**，等于没有止损，v1.6.0 的严重度分级表被架空。

- **降级禁令扩到 S3**：S1、S2 **不得降级为 S3 及以下**。
- **S1/S2 的定级与降级必须双签**：报告人 + 一位**非报告人**的 D 人格。
- 任何降级必须写明理由 + 双签记录，并记入 `decisions.md`。

**文件**：`protocol/bug-taxonomy.md`

### 修订二 · A2：A4 并行读取，不再「依次」

**病灶**：`personas/A4-汇总验证者.md` 要求 A4 **依次**读取 A1/A2/A3 的产物；`workflow` 里 A1–A3 本就是并行的，A4 却串行读——既慢，又诱导 A4 按读取顺序给结论加权。

- 职责行去「依次」；
- 行为准则 1 改为**并行读取 + 顺序呈现**（读可以并发，写进产物时按固定顺序，避免顺序偏袒）。

**文件**：`personas/A4-汇总验证者.md`

### 修订三 · A5：L8 与缓存契约的自相矛盾（一致性缺陷）

**病灶**：这是本版**最值得修的一处自身矛盾**。

- 铁律 **L8** 原文：「把目标人格的委任书**全文**作为角色定义传入」；
- 而 `selfrescue/cache-economy.md` 的度量项写着「**全文搬运次数：目标 0**」，`protocol/peer-channel.md` 更规定「在 payload 里贴全文 → 收件人**拒收**」。

**两条硬约束直接打架，晨怎么做都要违反一条。** 根因是把「**装载**（卡片要生效）」和「**搬运**（每次把全文物理粘进 payload）」混为一谈。

- **L8 与 `CORE.md` 第六节重写**：引入 `role_ref`（指向卡片）+ `role_load: static | inline`（装载方式）。
  - `static`（**同编号多轮复用，推荐**）：卡片进第 1 层静态区，**一次装载、后续共享、命中缓存**；
  - `inline`（首次 / 低频）：本次随提示内联 `role_text`。
- **判定标准**：子 Agent 动手前，它的角色定义里**确实有这张卡**——而不是「路径有没有出现」。
- **task 结构**加 `role_ref` / `role_load` 必填字段；缺则子 Agent 有权拒收（`kind: reject`，理由「委任书未锚定」）。
- **成本说明修正**：单张人格卡实为 **5–7k 字符**（早先「2–3k」低估约一倍）。

**文件**：`CORE.md`（L8、第六节 6.1/6.2）、`personas/chen.md`（委任三步 + 派发示例）、`workflow/01-new-project.md`（A1–A4 派发 YAML）、`workflow/04-escalation.md`（前提段）、`workflow/05-web-security.md`（并发示例注释）、`personas/web/chen-web.md`（75/97/131 + 头部）、`web/00-组索引.md`（头部）、`README.md`（§委任 + 目录树 + 人格册注脚），以及 **21 份主人格卡 + 35 份 Web 人格卡 + 5 份主组索引**的头部写法。

### 修订七 · A4：并发上限 8 的分批规则（**新增，填补空白**）

**病灶**：`CORE.md` 两处都写「同批并发上限 8 个实例…超过就分批」，但**全语料无一处定义「怎么分批」**。中规模项目里 `[A1,A2,A3]+[B1,B2,B3]+[C1,C2,C3,C4]+[D1,D2,D3,D4]` 加多实例极易触顶 8，晨每次都要临场决定且**不可复现**。

**修法**：`CORE.md` 6.3 新增 **规则 6.3.7 · 分批规则**（触顶时的唯一合法做法）：

```
1. 按组分批：同组同批，不做跨组混批。
2. 固定批容量（先小后大，给汇总人格留位置）：
     A 组：≤3（A4 不入批）  B 组：≤3（B4 不入批）
     C 组：≤4（C1–C4 全批）  D 组：≤4（D5/D6 不入批）
3. 任一时刻在飞的实例总数 ≤8；某组超过容量则拆成 #1..#n 两批串行。
4. 批次内不接收跨批依赖——依赖项自动落到下一批首。
```

**文件**：`CORE.md`（6.3 新增规则 7）

### 修订八 · B2：收敛数字由 B4 独立复算

**病灶**：`01-new-project.md` 阶段 9 是「**D6 出数字 → B4 判定**」，而 B4 判定用的**就是 D6 那份数字**——出数者与使用者同源 = **自证循环**。D6 的「等级校准」无人复核，B4 的"判定"只是对同一份数据的确认。

### 修订九 · B6：BUILD 门禁与规模对齐

**病灶**：极小/小的编制表**不含 C4**，但 BUILD 退出条件一律要「C4 安全层报告」→ **快车道永远过不了 BUILD 门禁**，只能靠"标记未做"绕过 → **门禁形同虚设**。而若为过门禁硬派 C4，正是阶段 0 批判的「极小任务派安全层」的浪费。


### 修订十 · C1：未读计数不再驱动轮询

**病灶**：`cache-economy.md` 规则 S4 明令「**不要为了告知进度而唤醒人格**」，但 `peer-channel.md` 的频道元数据设计了「未读计数」、自检项写着「inbox 有无**超过 1 轮**未读」、度量指标写着「未读滞留 ≤ 1」。**规则禁止它，指标却奖励它**——「未读滞留 ≤1 轮」必然诱导晨**定期轮询 inbox**，正是 S4 要禁的行为。

**修法**：
1. `peer-channel.md` 的 `state.json` 元数据去掉「未读计数」，改注「**仅落盘，不进任何自检**」；
2. 自检标题改「晨**每轮末执行一次**」，自选项从「超过 1 轮未读」改「**本轮内**未被读取」；
3. 末尾加「**对账后清零**」；
4. `cache-economy.md` 度量指标「未读消息滞留轮次」目标从「≤1」改「**轮末清零**」；
5. `cache-economy.md` 规则 S4 加连带约束段，显式说明两处曾打架、现统一为「频道只在轮末对账一次」。

**文件**：`protocol/peer-channel.md`、`selfrescue/cache-economy.md`

### 修订十一 · B3：修 bug 引入新 bug 的追踪（CH-2 加严）

**病灶**：CB-2 原门槛是「任一轮 **S1 级** bug 新增 ≥ 3」——**每轮各引入 2 个新 S1 可无限持续**且不触发任何刹车。而 D1 的基线比对职责**仅限「接手 / 重构轮」**，新项目的修复轮不强制 → **没有基线，CB-2 就无从计数**。

**修法**：
1. **CB-2 改为**：「**连续 2 轮**（新增 S1+S2）≥ 本轮修复数」，并写明计数口径（新增含 D1 用 `REG-` 前缀标记的回归 bug，类型码 `T-REG-*`）；
2. **D1 基线职责扩到每个修复轮**（删去"仅接手/重构"的限制），并说明它是 CB-2 成立的前提；
3. **D6 汇总增「引入率」** = `本轮新增（含 REG-）/ 本轮已修`，进入本轮概览数字表。

**文件**：`workflow/04-escalation.md`、`personas/D1-代码级跑测.md`、`personas/D6-分类汇总者.md`

### 修订十二 · A6：批次/单任务超时对账（**新增，填补「轮内》无计时」空白**）

**病灶**：v1.6.0 的预算是**轮**粒度的（`rounds_cap`），但**卡死发生在轮内**——一个慢实例能把整批拖住，而轮预算对此完全无感。现场表现为「一批里 7 个回来了、1 个卡住，晨干等」，且没人说得清"等多久算超时"。

**修法**：
1. **阶段 0.5 budget 加双阈值**：`per_task_timeout_hint`（单实例）/ `batch_timeout_hint`（整批墙钟）；
2. **新增「超时对账（轮内，不是轮末）」段**，三条纪律：
   - ① **超时不是失败，是信息**——产物标 `partial` 照样进汇总，注明缺口与 `confidence`；
   - ② **先收已回来的**，不等到底、不冻结整批；
   - ③ **替补同样要走委任协议**（`role_load`），替补拿到的是**它自己**那份委任书；
3. **`CORE.md` 的 `deadline_hint` 改为带阈值**（引用 `per_task_timeout_hint`，批次由 `batch_timeout_hint` 兜底）；
4. **`templates/state.json` / `state.md` 加三个位**：`per_task_timeout_hint` / `batch_timeout_hint` / `timed_out_instances`。

**文件**：`workflow/01-new-project.md`、`CORE.md`、`templates/state.json`、`templates/state.md`

### 修订十三 · C3：类型 → 负责视角（owner）表（**新增，堵检验盲区**）

**病灶**：`bug-taxonomy.md` 定义了类型码，但**部分类型没有明确的负责视角**（如 `T-FN-09/10`、`T-PF-*`、`T-UX-06`、`T-EN-06`、`T-LT-06`）。结果是「谁都没看到 → 报 0 条 → 看起来没问题」，而实情是**根本没人被派去查**。这是「伪装成干净的盲区」。

**修法**：
1. **`bug-taxonomy.md` 新增 §2.1「类型 → 负责视角（owner）」表**，覆盖全部类型组，把无主类型指配给**现有**视角（**不新增人格**，控制成本）；
2. **D6 汇总加「盲区检查」**：按表核对每个出现的类型码是否有其 owner 的报告；若某类型 0 条报告且 owner 本轮未派，D6 **必须**写「`<类型码>` 本轮无 owner 覆盖」——**这是盲区，不是没问题**，二者在报告里必须区分。

**文件**：`protocol/bug-taxonomy.md`、`personas/D6-分类汇总者.md`

### 修订十四 · B4：D4 否决权的闭环（复验门禁）

**病灶**：`CORE.md` §10 规定 AI 味治理权是「D4 报告 → B3 出方案 → C1/C3 执行」——**链条在执行处就断了**：没人检查改动是否真的消除了原判定，D4 的否决权有口无凭。这与 B3 的「需求收口权」不对称。

**修法**：新增 **§10.1 复验门禁（D4 闭环）**，五条：
1. **谁报告，谁复验**：C1/C3 不得自行宣布关闭，必须把改动坐标（文件 + 行号）回传 D4；
2. **D4 以证据坐标复验**，**不以"已按方案改了"为准**；
3. **D4 判「未达标」→ 不退回 B3 重出方案，直接升级 D6 仲裁**（避开 B3 自证）；
4. **AI 味项的关闭权归 D4**，与 B3 的需求收口权**对等**；
5. **复验留痕**：D4 在 `tests/bugs-D4-<轮次>.md` 追加「复验结论」段，不留口头结论。

**文件**：`CORE.md`（§10 治理权行 + 新增 §10.1）、`personas/D4-AI味猎手.md`（行为准则第 5 条 + 交付纪律）

### 修订十五 · B5：放行清单（**新增 `protocol/release-checklist.md`**）

**病灶**：DONE 门禁原文是「测试零 bug，或用户确认接受残余风险」——**单一数字门槛**，可被一个数字满足、也能被一句话绕开。而交付报告的 7 节结构只要求「**列出**」未验证项，**列出 = 诚实，不等于放行**：报告里写着「未验证项 12 条」照样能发。最典型的失败形态因此是 —— **流程全都走完了，东西不能跑。**

**修法**：新增 `protocol/release-checklist.md`（**进静态层**），规定 DONE 门禁的**七条硬勾选项**，任一未勾不得进 DONE：

```
[ ] 1. 未验证项 = 0，或用户已书面接受（留痕 decisions.md）
[ ] 2. C4 安全报告齐备（极小/小规模按 B6 分级要求）
[ ] 3. D4 复验通过（AI 味项，CORE §10.1）
[ ] 4. 回归基线一致（D1 已跑，差异逐条有解释）
[ ] 5. 可运行产物冒烟通过（不是"编译通过"，是"跑起来能用"）
[ ] 6. known-issue 每条有等级与理由（L3）
[ ] 7. 收敛数字经 B4 独立复算（不读 D6 汇总）
```

配套四件事：
1. **点名四种自欺**（「已列出」「按规模豁免了」「D4 说没问题了」「应该能跑」），并给一句话判据：**每一勾都要能指到一个文件、行号或原文；指不到，就是没勾**；
2. **`CORE.md` DONE 门禁接线**：`测试零 bug，或用户确认接受残余风险；**且放行清单七条全过**`；
3. **`01-new-project.md` 阶段 10 加「前置动作（强制）」**，交付报告结构新增**第 0 节「放行清单」**（逐条勾选 + 依据坐标）；
4. **明确它与收敛判据的分工**（防混淆）：收敛判据回答「bug 修完没有」，放行清单回答「**东西能不能交**」；**两者都过才进 DONE**。

### 追补（同日）：新增 `.zip` 分发产物

用户反馈"官方上传要求是 .zip"。**`.zip` 不是 `.tgz` 换扩展名** —— 两者是完全不同的格式，所以不能用改扩展名糊过去。

**查清了一件事**：DSH 的 `installBundle` 接受 **registry 包 / git 地址 / tarball / 绝对路径**，**不接受 `.zip`**。所以"官方要求 zip"是**分发/上传平台**那一侧的要求，与 DSH 的安装机制无关。两者不冲突：zip 给平台，对方解压后用目录路径安装。

**实现**：手写了一个**零依赖的最小 ZIP 写入器**（`_zip.mjs`，约 120 行，本地文件头 + 中央目录 + EOCD，deflate 压缩，UTF-8 文件名标志）。理由是本包的硬规则——**零外部依赖**——调 `Compress-Archive` 或 `zip` 会把构建绑到宿主工具上。

`_pack.mjs` 现在**用同一份已校验的文件清单同时产出两种格式**，并做了**三重验证**：

| 验证 | 用什么解压 | 结果 |
|---|---|---|
| tar 解压核对 | 系统 `tar` | 97 文件、90 语料与源一致 |
| zip 解压核对 | 系统 `tar -xf` | 97 文件逐字节一致 |
| zip 独立核对 | **.NET `ZipArchive`**（PowerShell `Expand-Archive`） | 97/97 逐字节一致 |

> **手写的写入器不能自己给自己背书。** 所以 zip 必须用**系统解压器读回来**才算验证过——而且用了两个不同的实现（GNU tar 的 zip 支持 + .NET ZipArchive），两个都认。

**过程中踩的一个坑（值得记）**：构建连炸两次，报 `writeUInt32LE` 收到 `-2119958528`。

我**第一次猜错了方向** —— 去改 `crc32` 的返回值（以为是有符号问题），改完照旧报错。真正的原因是同一行的另一处：`0o100644 << 16` 在 JS 里是**有符号 int32**（`0x81A40000` 最高位为 1），而 ZIP 的外部属性字段按无符号写。

**教训：报错给的是行号，不是原因。** 该先读那一行再动手，而不是先猜一个"常见原因"然后去改别处。

已加 **B5 组 8 项断言**把 ZIP 写入器纳入回归：签名、EOCD 条目数、中央目录偏移、**CRC32("hello") = 0x3610a686（已知标准值）**、外部属性无符号、deflate 有效性，另加中文路径往返。并新增 `_compare-extract.mjs` —— 一个可复用的"解压物 vs 源"逐字节比对器，可指定任意解压目录。

```

```

### 新增：GitHub 不可达处置（本机实测踩到）

写文档过程中本机 GitHub **突然不可达**（`git ls-remote` 连续 3 次 `Failed to connect to github.com port 443`，每次 22 秒超时）。诊断结论：

- `github.com` DNS 能解析（172.182.252.133），**TCP 443 不通**
- `registry.npmmirror.com` 通
- 系统代理 `127.0.0.1:10808` **开着**，但 **git 没配代理**
- 给 git 配上代理后 `ls-remote` 立刻 `exit=0`

**这是用户会真实遇到的问题，所以文档必须写**：

1. 症状（`Cannot access GitHub` / 22 秒超时）
2. 修法一：`git config --global http.proxy http://127.0.0.1:7890`（换成自己的端口）
3. 修法二：改用压缩包方式（完全绕开 GitHub）
4. **澄清一个常见误解**：npmmirror **解决不了这个问题**——它镜像的是 registry 上的包，不镜像 GitHub 仓库。这正是 Web 界面在你选镜像后提示 `Try another way` 的原因。

1. **`chen.md` 缺 `## 交付纪律` 段**。其余 21 份都有（因为它们是**被委任者**，纪律是"怎么干活"）；晨是**委任者**，纪律是"怎么管住班组"，所以补的是委任者版：只写 5 份产物、台账追加式不可改他人条目、人格产物回退给作者改、交付报告必须含三节、**不把"装好了"当成"能用"**。

## v1.1.3

**日期**：与 v1.1.2 同日
**类型**：**修正**（凭诊断原文定位到两个真实错误）

### 诊断原文（用户提供截图）

```
cds-mode (@local/dsh-cds-mode): cannot read properties of undefined (reading 'validate')
persistent-pwsh (@deepseek-ai/dsh-tool-pwsh-persistent): tool "pwsh" is already registered in this scope
```

### 错误一：`export const Config` 用了裸 JSON Schema 对象

cordis 校验行配置的方式是：

```js
// @deepseek-ai/cordis  resolveConfig()
if (!runtime.Config) return config
const result = runtime.Config["~standard"].validate(config)
```

它要求 `Config` 是一个 **schemastery / Standard-Schema 对象**（`z.object({...})`，`dsh-persona` 就是这么写的）。我导出的是手写的普通对象 `{ type: 'object', properties: {...} }`——它没有 `~standard`，于是 `.validate` 是 undefined，**在插件启动阶段抛错**，并被 `agent-preset-registry` 转成用户可见的「加载失败」。

**修正**：**去掉 `Config` 导出**。没有 schema 时 cordis 原样返回 config，而 `apply()` 本来就自己兜底默认值 + 自行校验（`corpusDir` 读不到、超 `maxChars` 都有指名道姓的报错），比 schema 校验的提示更有用。副作用：插件管理器不再能按 schema 展示/校验这三个字段——已知取舍。

### 错误二：`pwsh` 工具名在同一作用域注册两次

我从 `minimal` 预设抄了 `persistent-shell` 组（它注册**常驻**的 `pwsh`/`bash` 工具），同时又保留了 `preset-standard` 用的 `tool-pwsh`（**瞬时**工具）。**两套都装，工具名都是 `pwsh`**，注册表直接拒绝。

**修正**：删掉 `persistent-shell` 组，只保留 `tool-pwsh` —— 与 `standard` 预设一致。

### 验证（29 项断言，全部通过）

新增了**工具重名审计**：把每个预设作用域内所有启用行注册的工具名收集起来查重复。旧版校验没这一项，所以漏掉了这个 bug；现在它被制度化地挡住了。

| 组 | 覆盖 |
|---|---|
| A patch 编码 | 无 BOM、无乱码 |
| B 工具重名审计 | 两预设无重名；已移除 `persistent-pwsh`；保留 `tool-pwsh` |

2. **不要手写 `Config`；要么用 schemastery，要么不导出**（本次的错）。cordis 只认 Standard Schema。

## v1.1.2

**日期**：与 v1.1.1 同日
**类型**：**修正**（修复导致两个预设全部「加载失败」的根因）

### 根因

`index.js` 里有一行：

```js
import { PERSONA_PREFIX_SECTION } from '@deepseek-ai/dsh-system-prompt'
```

**这个包在 profile 的 `node_modules` 里不存在。** 实测：

```
profile\node_modules 顶层  =  .modules.yaml / .pnpm / @local    ← 没有 @deepseek-ai
从 bundle 真实目录 import '@deepseek-ai/dsh-system-prompt'  →  ERR_MODULE_NOT_FOUND
```

profile 用 `nodeLinker: hoisted`，而 DSH 自带的包**不在 profile 的 node_modules 里**。这个裸包名 import 解析失败 → `cds-mode` 行激活失败 → **两个预设都挂这一行，于是两个都标红「加载失败」**。

这是设计错误：为了一个字符串常量，引入了一个包依赖。

### 修正

`PERSONA_PREFIX_SECTION` 改为字面量 `'deployment:persona-prefix'`，源码注释里记了原因。**插件现在只 import `node:` 内建，零外部依赖**，从 bundle 真实位置加载已实测通过。

### 验证（这次是真实加载，不再是推断）

| 项 | 结果 |
|---|---|
| 非内建依赖 | **无** |
| 从 bundle 真实目录 `import()` | **OK**，exports = `Config, apply, inject, name` |
| 装载 | 11 份语料，**50,254 字符**，指纹 `b9af7285349f` |
| section | `deployment:persona-prefix`，order 0，interpolate false |
| 含全部 11 份语料 / 八条裁定 | 是 / 是 |
| 两次装载逐字节一致 | 是 |
| 语料缺失 / 超预算 | 均按预期抛错并给出修法 |

### 教训（写给下一个改这个 bundle 的人）

**bundle 里的插件只能用 `node:` 内建，或者把你依赖的包声明进 bundle 的 `dependencies` 并重装。** 裸写 `@deepseek-ai/*` 在本 profile 下必然解析失败，而失败表现是**预设整块标红**，不是一句清晰的"模块找不到"。

### 缓存影响
