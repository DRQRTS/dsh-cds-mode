# 主动进化 —— 小幅度自适应

> **本文件的定位**：CDS 早先是一个**不会学习的模式**。每个项目都从零开始：
> 不知道用户机器上装了什么、不知道上一版为什么被否掉、不知道用户讨厌什么写法。
> 于是同样的弯路要走第二遍。
>
> 本机制让晨在项目进行中**小幅度、持续地**观察与微调，把结论落盘，
> 下次同一项目直接受益。
>
> **三条边界（先说清楚，免得走偏）**：
> 1. **小幅度**：改的是默认值、表述方式、派发编制，**不动铁律、不动协议、不动人格卡**。
> 2. **项目内**：观察结果存在 `.cds/evolution.md`，**不跨项目**。跨用户的画像不做。
> 3. **不注入静态层**：观察结论**绝不进入系统提示前缀**（否则每轮缓存都失效，见下表）。

---

## 一、为什么必须落盘、且不能进前缀

这是本机制最容易做错的地方。有一个诱人的做法是：
「把用户偏好写进系统提示，这样每轮都记得」。

**这个做法是错的**，而且是本模式自己明令禁止的：

| 做法 | 后果 |
|---|---|
| 把偏好写进系统提示静态层 | 每次偏好更新 = **全局缓存失效一次**（`cache-economy.md` 规则 P4） |
| 偏好随会话变化实时改写前缀 | 每轮都失效，**比不学还贵** |
| **偏好落盘 `.cds/evolution.md`** | 前缀不动，缓存照旧命中；需要时随任务一起读 |

**一句话**：**学习成果是「数据」，放在文件里；不是「提示词」，不放进前缀。**

这与 `CORE.md` 的分层原则一致：把不变的东西放最前，把变化的东西放最后，
**把积累的东西放外面（文件里）**。

## 二、观察什么（四类，按价值排序）

### 类别 1 · 设备与工具链（**最早观察，收益最快**）

**为什么值得记**：这是纯客观事实，记一次省一辈子。
不知道用户机器上有没有 NVENC、用什么加壳、Python 是哪个版本 —— 每次都要试错。

```bash
# 一次性探测，结论写入 evolution.md
uname -s 2>/dev/null || ver                                    # 平台
python3 --version 2>/dev/null || py -3 --version               # Python
node --version                                                 # Node
ffmpeg -hide_banner -encoders 2>/dev/null | grep -c nvenc      # 有无硬件编码
git --version                                                  # 有无 git
```

| 观察项 | 记什么 | 怎么用 |
|---|---|---|
| 平台 | Windows / macOS / Linux | 命令写法（`python3` vs `py -3`；路径分隔符） |
| **实测可用性** | 不是「装没装」，是「**能不能跑**」 | **关键**：ffmpeg 列出 nvenc ≠ 可用（参数可能不被接受）。只记实测通过的 |
| 语言运行时 | 版本号 + 实际调用方式 | 避开应用商店的 `python3` 别名桩 |
| 已有工具链 | git / docker / 包管理器 | 决定交付形态（能不能给 Dockerfile） |
| 硬件瓶颈 | 核数 / 有无 GPU | 决定并发度（别把 CPU 吃满——用户会骂） |

> **探测纪律**：**只探测，不安装**。缺什么写进 `evolution.md` 的「缺口」栏，
> 需要时**问用户**，不许静默 `pip install` / `apt-get`。装东西是用户的决定。

### 类别 2 · 项目惯例（技术栈定下来之后）

| 观察项 | 例子 |
|---|---|
| 命名风格 | 用户自己的代码用 `snake_case` 还是 `camelCase` |
| 目录结构 | `src/` 还是 `app/`；测试放哪 |
| 依赖态度 | 能少则少 / 随便引 / 必须锁定版本 |
| 构建方式 | 有无现成构建脚本可以复用 |
| 已有代码风格 | 缩进、引号、注释密度、是否写 docstring |

**来源**：读用户**已有的代码**，不要问。「你的命名习惯是什么」是个坏问题——
答案在代码里，读一眼就有。

### 类别 3 · 用户偏好（**从行为推断，不靠问卷**）

| 信号 | 推断 | 记录为 |
|---|---|---|
| 用户否掉了一个方案，理由是「太重」 | 倾向轻量方案 | `pref: 偏好轻量，反感引入大依赖` |
| 用户多次改短文案 | 喜欢简洁 | `pref: 文案要短` |
| 用户说「别问了直接做」 | 授权代决策，讨厌流程 | `pref: 低提问容忍度，宁可代决策` |
| 用户改了交付物的某处细节 | 对该类细节有要求 | `pref: <具体是什么>` |
| 用户主动要求加功能 | 关注点在哪 | `pref: 重视 <X>，可主动多给` |
| 用户说「跟上次一样」 | 有既定形态 | `pref: 沿用 <某形态>` |

**纪律**：
- **必须写明「依据」**。不许写「用户喜欢蓝色」而没有依据——
  那是猜，不是观察。依据写「用户在 R-012 处把主色从蓝改成墨绿」。
- **一次观察不立结论**。同一信号出现 **≥2 次**才提升为「偏好」。
  单次记为「待观察」（见下）。
- **偏好可以被推翻**。用户改了主意就更新，不留旧结论。

### 类别 4 · 拒绝记录（**最有价值，也最容易被忽略**）

**用户否掉的东西，比用户要的东西信息量大。**

```md
| 被否方案 | 否掉理由（用户原话） | 提炼 |
|---|---|---|
| 用 React 重写 | 「太重了，就一个小页面」 | 反感为小需求引入大框架 |
| 加登录功能 | 「内部工具不需要」 | 内部工具默认不做账号体系 |
```

**用途**：**下次不再提**。这比「下次要提什么」更省时间——
它直接消掉了一整类会走错的岔路。

## 三、进化怎么发生（小幅度微调）

**关键**：进化**不是重写模式**，是**在既定参数上小幅移动**。四个可动旋钮：

| 旋钮 | 默认 | 可微调为 | 依据 |
|---|---|---|---|
| **提问量** | 按规模档 | 用户嫌烦 → 下调一档；用户嫌漏 → 上调 | 类别 3 |
| **表述深度** | 按 L1–L4 档 | 用户是高手却遇到啰嗦解释 → 直接给术语 | 类别 2/3 |
| **派发编制** | 按规模表 | 用户在意质量 → 该并行的真并行；用户在意快 → 再砍一档 | 类别 1/3 |
| **默认技术选型** | 中性 | 用户项目里已有一套栈 → 默认跟随 | 类别 2 |

**微调的三条硬规矩**：

1. **一次只动一个旋钮**。同时改三个，出了问题不知道是哪个引起的。
2. **改动必须可回滚**。写清「改前 → 改后 → 依据」，用户说不对立刻退回。
3. **不许动铁律 / 协议 / 人格卡**。那三样是模式的骨架，改它们是「版本变更」，
   要走 `03-iteration.md`，需用户授权。**进化只动参数，不动骨架。**

## 五、什么时候写（触发点）

**不要每轮都写**——那本身就是浪费。只在以下时机追加：

| 时机 | 写什么 |
|---|---|
| 项目开工（首次探测） | 类别 1 全部 |
| 用户否掉一个方案 | 类别 4（立即写，最容易忘） |
| 同一偏好信号第 2 次出现 | 从「待观察」提升到「已确认」 |
| 每轮结束 | 检查有无新的类别 2/3 信号 |
| 交付时 | 汇总「已生效的微调」，写进交付报告 |

**写入成本**：一次 5–10 行，追加不改动已有内容（append-only，同 `decisions.md`）。

## 六、与省钱机制的关系（重要）

**本机制天然省钱，前提是写对地方。**

| 做法 | 缓存影响 | 结论 |
|---|---|---|
| 观察写进 `.cds/evolution.md` | 前缀不动，缓存照常命中 | **正确** |
| 观察写进系统提示 | 每次更新全局失效 | **禁止** |
| 观察写进 `.cds/state.json` | 随状态一起读，中等成本 | 可接受（只放结论，不放原始观察） |
| 每轮都重读整个 evolution.md | 浪费上下文 | 用**末节「快速摘要」**代替 |

**优化**：在 `evolution.md` **最末**维护一段 ≤10 行的「快速摘要」，供日常读取；
完整内容只在需要时翻。这样日常成本接近 0。

```md
## 快速摘要（日常只读这一段）

- 平台 Windows / `python`（非 python3）/ 无 nvenc / 并发 ≤8
- 命名 snake_case，单测 pytest
- 偏好：文案短、反感重框架、低提问容忍度
- 不再提：React 类方案、内部工具的账号体系
```

**为什么放最末**：本文件是**按需读取**的（不在静态层），放哪不影响缓存。
放最末是为了「翻到末尾就看到摘要」，阅读习惯上的便利。

## 七、边界（不许越线的事）

| 不许做 | 为什么 |
|---|---|
| 跨项目建立用户画像 | 隐私边界。每个项目的 `.cds/` 是独立的 |
| 把偏好同步到全局配置 | 同上，且会污染其他项目 |
| 未经用户确认就改默认技术栈 | 选型是决策，不是观察能决定的 |
| 把观察结论当事实陈述给用户（「你喜欢蓝色对吧」） | 观察是概率性的，且用户被「总结」会不舒服 |
| 静默安装缺失的依赖 | 装东西是用户的决定 |
| 修改铁律 / 协议 / 人格卡 | 那是版本变更，走 03-iteration.md |
| 把 `.cds/evolution.md` 加进静态层 | 破坏缓存契约 |

**一句话原则**：**观察要勤，结论要慢，落盘要轻，越界要停。**
