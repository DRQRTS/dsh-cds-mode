# 其他组（E 组）· 索引

> **本文件是索引，不是人格卡。**
> 派发任务时，用 `role_ref` 指向下面表格里对应的人格卡并装载（`role_load: static`，见 `CORE.md` 第六节）。
> 只给路径而不装载 = 委任失败。

## 说明

本组**选择性出现**——仅在晨判定「需要」时才被调用，**不得默认出场**。
它们没有统一特质，或者说特质太复杂。本组是**开放组**：可按需继续添加各行各业可能需要的人格，不进行过于严谨的规划。

**共同规则**：
- 仅在晨判定"需要"时才被调用。
- 使用 `CORE.md` 的 `task` / `result` 结构。
- 产物落盘，命名带人格编号。
- 与其他组一样**不得直接对用户输出**（L1 铁律）。

**添加流程**（四步，不设审批）：
1. 新建 `personas/<编号>-<职能>.md`，套用现有委任书的结构（front-matter + 组说明 + 人格卡 + 交付纪律）；
2. 在本文件上表补一行；
3. 在 `cds/README.md` 的人格总览表补一行；
4. 若该人格有固定产物目录，在 `cds/protocol/artifacts.md` 补一行。

## E1 的分裂是本组唯一的层级例外

E1 可以创建 `E1.1`、`E1.2`… 并让它们**向自己**汇报，自己再汇总给晨。

**理由**：文字类工作天然可切分（骨架/口语化/节奏/校验），且切分后仍需统一文风，必须有一个汇总者。

**限制**：上限 5 个活跃子人格；编号不复用；必须登记注销状态到 `.cds/decisions.md`。

**其他组员（E2/E3）不得分裂。** A/B/C/D 组也不得自建**带编号的下属**（如 A1.1）；它们由晨直接并发多实例派出，不需要编号（见 `CORE.md` 第二节「并发是默认」与 DSH 裁定 1）。
