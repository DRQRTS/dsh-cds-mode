# 测试组（D 组）· 索引

> **本文件是索引，不是人格卡。**
> 派发任务时，用 `role_ref` 指向下面表格里对应的人格卡并装载（`role_load: static`，见 `CORE.md` 第六节）。
> 只给路径而不装载 = 委任失败。

## 组特质：真诚

它们绝对不会私藏任何一个 bug，而且极度善良——不希望看见项目因为这些 bug 毁于一旦，所以相当努力。

**真诚不是态度，是硬性纪律**：隐瞒 bug 在本模式中属于最严重的违规。

**共同禁令**：
- 不隐藏、不修饰、不"顺手修掉而不报告"。
- 不把"我没测到"说成"没有问题"。
- 不向上游示好：测试组的报告不是给开发组面子用的。
- 不向用户直接输出（L1 铁律）。

**统一 bug 条目格式**：

```yaml
- id: BUG-0001
  title: <一句话，含现象>
  level: S1|S2|S3|S4|S5      # 五级分类法，见 protocol/bug-taxonomy.md
  type: <类型分类法代码，见 protocol/bug-taxonomy.md>
  found_by: D1
  round: 1
  repro:            # 复现步骤，必须逐步可执行
    - <步骤>
  expected: <期望>
  actual: <实际>
  evidence: <日志/截图路径/输出片段>
  impact: <影响范围：哪些用户、哪些功能、多严重>
  guess_cause: <推测根因，可写"未知">
  suggestion: <修复建议，可写"无建议">
  confidence: 高|中|低
```

**产物**：`tests/bugs-D<n>-<轮次>.md`（由 D6 汇总为 `tests/00-bug-summary-<轮次>.md`）

## 典型派发顺序

```
D1 ┐
D2 ├
D3 ├─ 并行 ──> D6 ──> B4（TRIAGE）
D4 ┘

C4 ──> D5 ──┘   （D5 单列：输入来自 C4，不与 D1–D4 同批）
```

**D1–D4 并行**，四者前缀一致，共享缓存。D6 必须等全部完成。
**D5 不在这一批里**——它的输入是 C4 产出的红队入口，晚于 D1–D4 就绪；与 D1–D4 同批要么空跑要么拖慢全批。详见下节。

## D5 的输入是特例

D5 **不接受源码**。它的唯一输入是 C4 产出的 `tests/D5-redteam-entry.md`（红队入口说明：部署地址、可注册账号、公开接口清单）。

派发 D5 时**不要**给它 `src/` 路径。给了源码，它的结论置信度必须降为「低」并声明。

## D6 的两个职责

1. **汇总**：去重、等级校准、交叉印证、净变化统计 —— **净变化数字是本模式收敛判定的唯一依据**。
2. **仲裁**：门禁拉锯（C 组说设计稿不完整 / B4 说已收口）由 D6 裁决，**以"开发组能否无提问开工"为客观标准**。

## 降级映射

| 失效 | 替补 | 备注 |
|---|---|---|
| D1 | D2 | 代码级覆盖下降 |
| D2 | D1 | 体验类 bug 可能漏检 |
| D3 | D1 | 长远 bug 覆盖下降 |
| D4 | B3 | AI 味治理转入设计侧，检测能力下降 |
| D5 | C4（仅自查，非盲测） | **盲测假设被破坏，结论置信度降为「低」**，必须声明 |
| D6 | B4 | 分类汇总并入设计组，注意保持分类法结构 |
