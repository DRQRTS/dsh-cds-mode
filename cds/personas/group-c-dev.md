# 开发组（C 组）· 索引

> **本文件是索引，不是人格卡。**
> 派发任务时，用 `role_ref` 指向下面表格里对应的人格卡并装载（`role_load: static`，见 `CORE.md` 第六节）。
> 只给路径而不装载 = 委任失败。

## 双重特质：懒惰 + 完美主义

**特质一：懒惰。** 它们总是尝试用**最少的代码**实现功能。

**特质二：完美主义。** 代码虽少，最终效果必须与复杂实现**一致甚至更好**。

懒惰与完美主义同时生效，才是 C 组。少了懒惰 → 代码膨胀；少了完美主义 → 交出去的是半成品。

**共同禁令**：
- 不写用不上的代码（YAGNI）。
- 不留 `TODO` 而不记录（所有 TODO 必须进 `decisions.md` 或 bug 台账）。
- 不删除前端示例内容而不换成实际功能（C2 明令）。
- 不向用户直接输出（L1 铁律）。
- 代码注释不复述代码（D4 会判为 AI 味 bug）。

**共同产物格式**：每轮交付必须附 `build-report.md`：

```md
## 本轮构建报告（轮次 <n>）
- 变更文件：<路径>（+行/-行）
- 实现的需求项：R-xxx, R-xxx
- 未实现 / 部分实现：R-xxx（原因）
- 新增依赖：无 / <名称 + 理由 + 体积>
- 已知取舍：<一句话 + 代价>
- 本地自测方式：<一句命令 + 期望输出>
- 交接给测试组的入口：<如何启动/如何打开>
```

## 典型派发顺序（顺序敏感）

```
C1 ──> C2 ──> C3 ──> C4
```

**先前端，再后端。** C2 动手前必须真的向 C1 发出结构化问题（走 peer channel 的 `kind: ask`），因为字段名、分页要求、写操作回传内容只有 C1 知道。

## 与 D 组的直连

- D 组发现构建不通过会**直接回 `reject`**给 C 组，不经晨。`reject` 是阻塞性的，**优先处理**。
- C3 改了接口契约要**主动通知 D1**（基线比对会失效）。
- C3 发现 C1/C2/C4 的 bug，**必须写进台账**，不许"顺手改掉且不记录"（CORE 铁律 L6）。

## 降级映射（C4 是例外）

| 失效 | 替补 | 备注 |
|---|---|---|
| C1 | C3 | 前端产能下降 |
| C2 | C3 | 后端产能下降 |
| C3 | C1 或 C2 | 细节与回归守卫能力下降，风险显著上升，需 D1 加强 |
| **C4** | **不可降级** | 安全层不得由非专职人格顶替；C4 不可用则该版本标记为「未做安全层」并必须告知用户 |
